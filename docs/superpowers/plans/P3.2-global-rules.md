# P3.2 Global rules Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every widget of the Union style square and free of lines before any family is restyled. Every corner radius becomes zero except on a round widget. Every border, outline and widget shadow goes. The tones of each state become variables in the style, generated from the tokens. The plan also shows by pixels that no widget drawn by Union in a Qt Widgets application keeps a rounded corner or an outline.

**Architecture:** The rules of the Breeze copy in `parts/union-style/amber/contents/css/` are edited where they are written (my call). A trailing file of overrides was ruled out: Union CSS gives a `button` rule priority over a `*` rule, so a global override would lose to every rule of a widget family. The spec in `tools/src/lib/union-style.spec.mjs` reads every declaration, at every depth of nesting, and fails on a radius, border, outline or widget shadow that comes back. A new generator part writes `contents/css/tokens.css` from `prototype/tokens.css`, and `style.css` imports it. The pixel check renders each widget into an image at scale 1 from a PySide6 probe in P2.3's nested session. A new `image frame` command reads those images for rounded corners and lines. Before anything is edited, the same probe runs with the unchanged Breeze style to prove that the check catches both.

**Tech Stack:** Union CSS (`plasma-union` 6.8.2), Node 24 with `node:test`, the `generate`, `image` and `tokens` tools, PySide6 6.11.2, the nested `kwin_wayland` session of P2.3/P3.1 (`tmp/check-colour-scheme/`), Dolphin.

**Spec:** `docs/product/roadmap.md` (row P3.2, the note under Step 3), `docs/architecture/design-language.md` ("Principles", "Widgets", "Shadow"), `docs/architecture/platform.md` ("Union", "Union CSS", "Tools and switches", its "Unverified" table), `docs/architecture/overview.md` ("How it fits together"), `docs/architecture/tooling.md` ("Rules for every tool"), `docs/architecture/decisions.md` (D-4, D-24, D-25, D-92, D-96).

- **Anti-goals.** After this plan, no widget of the style has a rounded corner, a border, an outline or a shadow, with these exceptions:

There are exactly five (my call): the indicator of `radiobutton, radiodelegate, menuitem.exclusive` (`check.css`), `roundbutton` (`button.css`), `dial` (`bars.css`), `pageindicatordelegate` (`application.css`) and `selectionrectanglehandle` (`tables.css`).
  - **The switch is not a round widget.** Its track and its handle become square, as the slider's thumb is (design language, "Ranges"). (my call; the owner may want the handle round)
  - **A shadow stays only in `popup.css`**, on menus, popups, tooltips and dialogs. Whether Union draws it is P3.8's question. Every other `box-shadow`, `--button-shadow` and the card's shadow included, is `none` (design language, "Shadow").
- **Separators lose their fill.** `toolseparator` (`button.css`), `menuseparator` (`popup.css`) and the splitter's `& > separator` (`application.css`) keep their size, and their `background-color` is removed, so they show as a gap with no line. P3.6 and P3.8 give them their final size (the menu separator becomes an 8 px gap).
- **Focus is not shown on a family until its own plan restyles it** (my call). Removing borders and outlines removes whatever focus Breeze drew with them. The style is not installed, so nobody uses it in the meantime. Task 2 records what Breeze draws, so that P3.3 to P3.8 know what they are replacing.
- **Edited rules stay where they were.** Change the value, or delete the declaration where this plan says to. Do not reorder or reformat Breeze's rules, so that `git diff` shows only this plan's changes. A rule that only sets a colour, such as `border-color`, stays even when no border is left to colour, because each family's plan rewrites its own rules.
- **Amber's own files in the style are BSD-2-Clause**, like the rest of the folder (my call). Each starts with `SPDX-License-Identifier: BSD-2-Clause` and `SPDX-FileCopyrightText: 2026 <git config user.name>`.
- Files of the nested session and the probe stay in `tmp/` and are not committed, as in P2.3 and P3.1.

## Review Focus

- **A check that passes everything.** If the probe's images, or `image frame` itself, cannot see a rounded corner or a line, every amber run passes for the wrong reason. This is pinned in Task 2, Step 4: with the unchanged Breeze style, `image frame` must report rounded corners and lines on the push button, the line edit and the combo box.
- **A state that never reaches the widget.** `QWidget.render()` draws a hovered, focused or pressed widget only if the state really applies: the hover attribute, keyboard focus with its reason, `setDown`. A state that silently does not apply draws as at rest and hides the border that state adds. This is pinned in Task 2, Step 4: under Breeze, each state's image must differ from the widget's at-rest image, or that state is written down as not reached and checked on screen instead.
- **A line that comes back in a nested state.** Breeze sets borders again in `&:hovered`, `&:visual-focus`, `&:disabled`, `.inactive &` and `& > handle` blocks. A spec that reads only top-level declarations would miss them. This is pinned in Task 4, Step 1: the declaration reader is tested on nested blocks, and the frame check covers every state.
- **A generated variable that shadows one of Breeze's.** If a token name is also declared in `variables.css` or by a widget family, one silently overrides the other. This is pinned in Task 3, Step 1: no name in `UNION_TOKENS` is declared in any other file of the style.
- **`render()` does not match the screen.** The probe draws widgets into an image, while Dolphin draws them in a window that KWin composes. Menus are windows of their own, and Qt may draw some frames itself. This is pinned in Task 5, Step 3: a screenshot of Dolphin and of its settings dialog is read with `image greys` and checked by eye for corners and lines.

### Task 1: `image frame`

**Files:**
- Modify: `tools/src/lib/image.mjs`, `tools/src/lib/image.spec.mjs`, `tools/src/bin/image.mjs`, `tools/src/bin/image.spec.mjs`
- Modify: `.claude/skills/ai-tools/references/tools.md` (section `image`), `docs/architecture/tooling.md` if it lists the commands

**Interfaces:**
- Consumes: `decodePng`, `encodePng({ width, height, pixels })` from `png.mjs`. The image is `{ width, height, pixels }` with RGBA pixels, as `coolGreys` takes it.
- Produces: `frame(image, { surface, region }) → { drawn: boolean, box: {x, y, w, h} | null, corners: { tl, tr, bl, br }, sides: { top, right, bottom, left } }`. Each corner is `'square' | 'rounded' | 'not judged'`, and each side is `'clear' | 'line' | 'not judged'`. A side that is `'line'` also carries its colour and thickness, as `sides.top = 'line'` with `lines.top = { hex, thickness }`. CLI: `image frame <png> --surface <hex> [--region x,y,w,h] [--json]`. It exits 1 when a corner is `'rounded'` or a side is `'line'`, 0 otherwise, and 2 on a wrong command line, as the other commands do.

The rules, which the tests pin (my call):
1. **Box**: the bounding box of every pixel that is not the surface colour within ±1 on each channel. A pixel that is fully transparent counts as surface. With no such pixel: `drawn: false`, every corner and side is `'not judged'`, and the exit code is 0.
2. **Filled side**: a side of the box is filled when at least half of the pixels on its outer row or column are not surface. Only a filled side is judged, and a corner only when both its sides are. Text alone never fills a side, and neither does a circle, whose outer rows are short.
3. **Rounded corner**: when both sides of a corner are filled and the corner pixel is surface (±1), or a blend whose distance to surface is less than half its distance to the colour 3 px in along the diagonal, the corner is `'rounded'`. Otherwise it is `'square'`.
4. **Line**: the colour of a filled side at depth *d* is the most common colour on the row or column *d* px inside the box, corners excluded. If the colour at depth 0 differs from the colour at depth 3 by more than ±1 on a channel, take the thickness *t*: the number of rows from depth 0 with that same colour. *t* of 1 or 2 is a `'line'`. *t* of 3 or more is a band, such as a focus bar or a block marker, and the side is `'clear'`.

- [ ] **Step 1: Write the failing tests** in `image.spec.mjs`. Each test builds a picture with `encodePng`/raw pixels on surface `#25221f`:
  - a 40×20 rectangle of `#312e29` → `drawn`, every corner `'square'`, every side `'clear'`;
  - the same with a 1 px border of `#3c3832` → every side `'line'`, with `lines.top` `{ hex: '#3c3832', thickness: 1 }`;
  - the same with a 2 px border → `'line'` with thickness 2;
  - a rectangle with a 3 px `#d1b072` bar at its foot → bottom `'clear'`;
  - a rectangle with corners cut by a radius of 5 (pixels inside the circle filled, the corner pixel surface) → every corner `'rounded'`;
  - a 16 px filled circle → every corner and side `'not judged'` (a round widget is not judged; the spec of Task 4 guards it);
  - a 30×20 rectangle with a radius of 10, as Breeze's slider thumb → every corner `'rounded'`;
  - a few scattered pixels, like text → no side filled, everything `'not judged'`;
  - an all-surface picture → `drawn: false`;
  - a transparent picture with a square rectangle → `'square'` and `'clear'`.

  In `bin/image.spec.mjs`, write PNGs to a temporary folder and check the following: exit 1 and a line naming the side, colour and thickness for the border picture; exit 0 for the plain rectangle; exit 2 for a missing `--surface` and for `--surface` that is not a hex colour; and `--json` printing the object above.

### Task 3: The tokens in the style

**Files:**

- Modify: `tools/src/lib/generate.mjs` (`PARTS`), `tools/src/bin/generate.mjs` (a command), `tools/src/lib/union-style.spec.mjs`, `parts/union-style/amber/contents/css/style.css`, `.claude/skills/ai-tools/references/tools.md` (section `generate`)

**Interfaces:**
- Consumes: `loadTokens()`, `resolveToken(tokens, name)`, `formatTokenValue(value)` from `tokens.mjs`, used as `colour-scheme.mjs` uses them.
- Produces: `UNION_TOKENS: string[]` and `formatUnionTokens(tokens): string` in `union-tokens.mjs`, the part `'union-style-tokens'` in `PARTS`, and the command `generate union-style-tokens [--write] [--json]`. Every later plan of Step 3 uses these variable names: `var(--tone-3)`, `var(--raised-focus)` and so on.

`UNION_TOKENS` (my call: every token a widget uses, and no token of the decoration, the terminal or the editor), in this order:
`tone-0`, `tone-1`, `tone-2`, `tone-3`, `tone-4`, `text`, `text-dim`, `accent`, `on-accent`, `danger`, `on-danger`, `well`, `raised-focus`, `well-focus`, `surface-focus`, `well-focus-edge`, `well-focus-edge-width`, `accent-hover`, `accent-pressed`, `toggle`, `toggle-focus`, `track`, `thumb`, `thumb-hover`, `thumb-pressed`, `selected`, `marker-width`, `popup`.

The file's form is fixed. Each value is resolved to a plain colour or length, and a token that refers to another keeps the reference as a comment:

```css
/*
 * SPDX-License-Identifier: BSD-2-Clause
 * SPDX-FileCopyrightText: 2026 <owner>
 *
 * Generated from prototype/tokens.css by `generate union-style-tokens`.
 * Do not edit: change the token and generate again.
 */

:root {
    --tone-0: #151413;
    ...
    --well: #151413; /* var(--tone-0) */
    ...
}
```

The `<owner>` is the last author in `metadata.json`.

All widget tokens go into the style, not only those the colour scheme has no role for. This replaces the overview's rule that the style takes a colour from the scheme wherever a role matches (my call, D-97). The reason: a family's rules then name the tone the design language names (`var(--tone-4)`, not the Button set's `alternate`). The rules of Breeze that read the scheme stay until each family's plan rewrites them.
