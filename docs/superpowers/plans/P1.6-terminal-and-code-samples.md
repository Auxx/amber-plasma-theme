# P1.6 Terminal and code samples Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A third prototype page, `prototype/samples.html`, shows the terminal colours on a mock Konsole window and the editor theme on a mock Kate window, both filled with realistic content. Every terminal and syntax colour is a token with contrast pairs, and every one but ANSI black passes. Beside the samples are candidates for the terminal background and for the text selection, each with its measured contrast.

**Architecture:** The pattern of P1.1 to P1.5 continues. The new colours become tokens in `prototype/tokens.css`, with pairs in `prototype/contrast-pairs.json`. The syntax colours are not new hues: each is a `var()` of an ANSI colour, so Kate and Konsole share one palette. The page links `window.css` for its two windows, `widgets.css` for their tab bars and `gallery.css` for the page, its families and its candidates, and draws the samples in a new `samples.css`. Each coloured run of text is a `<span>` with one class, `ansi-<name>` or `syn-<name>`, which reads the token of the same name. A new spec, `prototype-samples.spec.mjs`, checks in Chrome that every span and surface reads its token. The page has no script.

**Tech Stack:** HTML and CSS opened as `file://` (D-35); Node 24 ES modules, `node:test`, `node:assert/strict`; the existing `tokens.mjs`, `prototype-check.mjs` and `browser.mjs` (playwright-core with the installed Chrome, D-46). No new dependency.

**Spec:** `docs/product/roadmap.md` (P1.6: "Every colour except ANSI black, which is exempt, has a contrast pair and passes"), `docs/product/vision.md` (goal 7: Konsole's terminal area and Kate's editor area match the frame around them), `docs/architecture/design-language.md` (Starting tokens: terminal and syntax colours are muted, warm-shifted hues approved in the prototype), `docs/architecture/accessibility.md` (rule 3), `docs/architecture/decisions.md` (D-12, D-20, D-53), `docs/architecture/overview.md` (the editor theme and terminal colours files), `docs/superpowers/specs/2026-11-10-amber-theme-design.md` (prototype: "a terminal sample and a code sample showing the Konsole and Kate colours"). For the candidate markup and the gallery's conventions, see `docs/superpowers/plans/P1.5-gallery-navigation-views-and-popups.md`.

## Review Focus

- **A colour that passes on the editor but not under the cursor's line or a selection.** A syntax colour is read on three backgrounds, and the selection is the hardest. Pinned by the 21 pairs and by `keeps syntax colours readable on every editor background` (Task 1).
- **A span that falls back to the browser's colour.** A misspelt class (`ansi-bright_red`, `syn-keywords`) leaves a run of text in `--text` and nobody notices. Pinned by `colours every span from its token` (Task 3), which fails on a class with no token.
- **Reverse video and coloured backgrounds.** `less`, `htop` and many prompts draw ANSI colours as backgrounds with the terminal background as text. Contrast is symmetric, so those pairs are the same ratios as the 15 pairs on `terminal`; ANSI black as text is darker still, so it passes wherever `terminal` does. No new pair; the accessibility document says so (Task 6).
- **The gutter drifting from its lines.** Line numbers that do not sit level with their code look broken, most of all next to the current line. Pinned by `lines up the gutter with the code` (Task 4).
- **A line sneaking into the editor.** A border on the gutter or the current line, or a 1 px gap of another tone between them, is a hairline. Pinned by `draws the samples with no line` (Tasks 3 and 4), with P1.5's line rule.
