# P3.3 Buttons Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Union style draws push buttons, the primary button, tool buttons and read-only combo boxes with the tones, text colours and heights of the prototype's gallery in every state. This is checked by pixels in a Qt Widgets application and by eye in Dolphin.

**Architecture:** The button rules of `parts/union-style/amber/contents/css/button.css` are rewritten where they stand, using only the variables of the generated `tokens.css` (D-97). The P3.2 probe (`tmp/check-colour-scheme/widgets.py`) gets combined states, a choice of surface and a filter for one family. Two new tool commands turn "matches the prototype" into a check that runs again in P3.4 to P3.8. `browser states` reads the expected background and text of each state row from `prototype/gallery.html`. `image states` reads the fill and text of each probe image and compares the two, state by state, by hex. Task 1 first finds out whether Union can tell a default push button from a normal one in Qt Widgets. The plugin's strings name no such hint, and the primary button depends on it.

**Tech Stack:** Union CSS (`plasma-union` 6.8.2), Node 24 with `node:test`, the `browser`, `image`, `generate` and `tokens` tools, PySide6 6.11.2, the nested `kwin_wayland` session of P2.3 to P3.2 (`tmp/check-colour-scheme/`), Dolphin.

**Spec:** `docs/product/roadmap.md` (row P3.3 and the notes under Step 3), `docs/architecture/design-language.md` ("Widgets": the first table and the bullets on precedence, pressed, a checked tool button and the primary button), `prototype/widgets.css` and `prototype/gallery.html` (the rows `button`, `primary`, `tool-button` and `combo`), `docs/architecture/platform.md` ("Union", "Union CSS", "Tools and switches"), `docs/architecture/decisions.md` (D-4, D-64, D-76, D-97, D-98), `docs/superpowers/plans/P3.2-global-rules.md` (the probe and its outcome).

  A checked tool button keeps `accent` text in every state. Hovered, it is `tone-4`. Focused and pressed, it takes an unchecked tool button's tone. Precedence: pressed beats focused, and focused beats hovered. A disabled widget never changes. The combo box's arrow is coloured as its text.
- **Decisions of this plan** (my call, recorded as D-99 in Task 5):

  - `roundbutton` and `delaybutton` take the push button's tones. They are drawn only in Qt Quick, which is not checked in this plan.
  - The inactive window changes no button. The design language gives "inactive" to windows and decorations only.
- **Heights** (the prototype: `height: 30px`, `padding: 0 12px`, and `0 8px` for a tool button): the push button, the read-only combo box and a text-only tool button are 30 px high at scale 1. Their horizontal padding is 12 px, or 8 px for a tool button. If Qt's size hint keeps a widget taller than 30 px, record the height and the reason in `platform.md`. Keep the nearest height that can be reached. This is not a reason to stop.

## Review Focus

- **Two states at once.** Under the pointer, a focused button is hovered too, and a pressed button is usually focused. If Union resolves `:hovered` after `:visual-focus`, a focused button turns tone 4 when the mouse passes over it, which breaks the precedence rule. This is pinned in Task 1, Step 4, which asks how Union orders states, and in Task 4, Step 2: the probe draws `hovered-focused`, `focused-pressed` and `disabled-hovered`, and `image states` checks each.
- **A no-fill tool button that reads as filled.** A tool button at rest has no fill. On magenta, the probe would see magenta, and on tone 2 it would see tone 2, but the prototype shows it on a tone 0 toolbar. This is pinned in Task 2: `browser states` takes the background of the nearest ancestor that has one. In Task 4, the tool buttons are drawn on tone 0 (`--surface '#151413'`), so both sides give `tone-0`.
- **Text read as the fill, or anti-aliasing read as the text.** A short label on a wide button is mostly fill, but a tool button with only a few letters is not. Blended edge pixels can outnumber the solid core of thin glyphs. This is pinned in Task 2, Step 1: `image states` is tested on a synthetic button whose text is a few solid strokes with blended edges, and on an image with no text.
- **The default button moves.** In a Qt Widgets dialog every push button is auto-default, and whichever has focus becomes the default. So the primary tone can jump to Cancel when Cancel is tabbed to. This is pinned in Task 4, Step 4: in Dolphin's settings dialog, tab from OK to Cancel, and write down where the primary tone goes. If it moves, the owner hears of it with the outcome.
- **A colour the scheme still feeds.** A Breeze declaration that reads `custom-color(...)` and is left in a button block would draw a colour of the colour scheme. It may equal a token today and drift later. This is pinned in Task 3, Step 1: the spec allows only `var(--<token>)`, `none` and `transparent` for colours in the button blocks.

### Task 2: `browser states` and `image states`

**Files:**
- Modify: `tools/src/lib/browser.mjs`, `tools/src/lib/browser.spec.mjs`, `tools/src/bin/browser.mjs`, `tools/src/bin/browser.spec.mjs`
- Modify: `tools/src/lib/image.mjs`, `tools/src/lib/image.spec.mjs`, `tools/src/bin/image.mjs`, `tools/src/bin/image.spec.mjs`
- Modify: `.claude/skills/ai-tools/references/tools.md` (sections `browser` and `image`), and `docs/architecture/tooling.md` if it lists the commands

**Interfaces:**
- Consumes: the gallery's markup. `.state-row[data-widget=<name>]` holds `.state[data-state=<state>]` elements, each holding one widget. Also the existing `colours` code of `browser` (computed colours named as tokens), and `decodePng` from `png.mjs`.
- Produces:
  - `browser states <page> --widget <name> --selector <css> [--json]`. For each `.state` of that row, in document order, it gives `{ state, background: { hex, tokens }, text: { hex, tokens } }`. `<css>` finds the widget inside each `.state`. The background is the element's own computed background, or, when that is transparent, the nearest ancestor's that is not. `tokens` lists every token with exactly that hex, since `tone-0`, `well`, `toggle` and `track` share one. Exits 1 when the row or a widget is missing.
  - `fill(image, { surface }) → { background: hex, text: hex | null }` in `image.mjs`. `background` is the most common colour. `text` is the most common colour that is neither the background nor a blend of the background and another colour of the image, that is, a colour lying on the line from the background to a commoner colour within ±2 per channel. It must also cover at least 0.5 % of the pixels; otherwise it is `null`. Pixels within ±1 of `surface` are left out of both.
  - `image states <folder> --expect <json> --case <probe-name> [--surface <hex>] [--json]`. It reads `<folder>/manifest.json`, takes the images of `<probe-name>`, and matches each probe state to the expectation of the same name. It compares `background` and `text` by hex within ±1 per channel. The text prints one line per state, `ok` or the two hexes with their tokens, and a state in the probe that has no expectation, or the other way round, is listed as "not compared". Exits 1 on any mismatch, and 0 when everything compared matches. A state named only by the probe, such as `hovered-focused`, is matched through `--alias hovered-focused=focused`, which may be repeated.

- [ ] **Step 1: Write the failing tests.**
  - `browser.spec.mjs`: on a small fixture page with two `.state-row`s (a `button` row with `rest`/`hovered` and a tool button on a `#151413` strip with no fill of its own), `states` gives the `hovered` row `tone-4` and the tool button's `rest` row `background.hex` `#151413`, with `tokens` containing `tone-0` and `well`. `bin`: exit 1 for a missing `data-widget`, and exit 2 without `--widget`.
  - `image.spec.mjs`:
    - a 60×30 `#312e29` image with three 2 px wide strokes of `#e8e3da` 12 px tall, each edged by `#8d8981` blend pixels, gives `{ background: '#312e29', text: '#e8e3da' }`;
    - a plain `#3c3832` image gives `text: null`;
    - with `surface: '#ff00ff'`, a 40×20 button on a magenta 60×40 field gives the button's colour as the background;
    - a 40×30 image that is a quarter text gives the text colour, not the fill, as `text`.
  - `bin/image.spec.mjs`: a temporary folder with a `manifest.json` and two PNGs, and an expectation file. Exit 0 when both match, exit 1 with a line naming the state and both hexes when one does not, `--alias` maps a state, and exit 2 without `--case`.
