# P0.4 Spike: square decoration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Find out whether an Aurorae theme on the owner's machine can draw a window decoration with square corners and no border line on any edge, and write the answer into the platform document.

**Architecture:** A throwaway Aurorae theme, `amber-spike`, is installed for the user in `~/.local/share/aurorae/themes/`. It is never selected in the owner's session. A second, nested KWin is started as a window inside the owner's session, with its own configuration folder, its own cache folder and its own D-Bus session, and that KWin alone is told to use the theme. A small PySide6 window is opened inside it, pictures are taken, and the pixels at the corners and edges are read. Nothing of the spike is kept except its findings.

**Tech Stack:** `kwin` 6.8.2 (`kwin_wayland`, nested), `aurorae` 6.8.2 (the SVG engine `org.kde.kwin.aurorae`), `kdecoration` 6.8.2, SVG, Python 3 with PySide6 6.11.2, `dbus-run-session`.

**Spec:** `docs/architecture/platform.md` ("Window decoration", its "Unverified" table and "Spike findings"), `docs/architecture/design-language.md` ("Window decoration"), `docs/architecture/decisions.md` (D-2, D-3, D-13, D-34, D-38), `docs/product/roadmap.md` (row P0.4).

This is a spike, so the plan has no tests to write first. Each step is an action with something to observe, and what is observed is noted for Task 5. The spike's theme has no window buttons to match the prototype and no shadow: buttons are P5.2 and the shadow is P5.3.

## Global Constraints

- Use the glossary's words (`docs/product/glossary.md`); British spelling.
- **Never change the owner's system settings.** Nothing under `~/.config` is created or edited. The owner's `~/.config/kwinrc` is the same file before and after (compare its checksum in Task 1 and Task 5). The owner's running KWin is never restarted, replaced or reconfigured: no `kwin_wayland --replace`, no `qdbus org.kde.KWin /KWin reconfigure` on the owner's session bus, no `plasma-apply-aurorae`, no `kwriteconfig6` without `--file` pointing into the spike's folder.
- Write nothing under `/usr`.
- All spike files live in `tmp/spike-decoration/` in the repository (`tmp/` is ignored by git). None is committed. The one exception is the installed copy of the theme in `~/.local/share/aurorae/themes/amber-spike/`, which Task 5 removes.
- The theme's identifier is `amber-spike`, not `amber`, so that it can never be mistaken for the real decoration of P5.1.
- The nested KWin always runs with all four of: `XDG_CONFIG_HOME=tmp/spike-decoration/config`, `XDG_CACHE_HOME=tmp/spike-decoration/cache`, its own bus from `dbus-run-session`, and its own socket name `wayland-amber-spike`. `XDG_DATA_HOME` is left alone, so that it finds the theme where the real decoration will be installed.
- Colours come from the design language: tone 0 `#151413` for the title bar; tone 1 `#1c1a18`. For finding stray pixels the spike also uses loud colours that appear nowhere else: magenta `#ff00ff` and green `#00ff00`.
- A fact goes into the platform document as "verified" with the date of the run only if it was seen on this machine in this spike.
- **Stop and ask the owner** if the corners cannot be square or a line cannot be removed, or if no way is found to see the theme without changing a system setting. Write the reason into the platform document first (Task 5), then stop: a compiled decoration, Breeze's own decoration or a known gap is the owner's decision (D-38).

## Review Focus

Ways this spike could give a wrong answer, most likely first. Each is pinned by a step.

- The nested KWin is not drawing the spike's theme at all (it fell back to Breeze's decoration, or the test window drew its own title bar), so nothing seen says anything about Aurorae. Pinned in Task 2, Step 4: the title bar must be magenta.
- A line that exists only at a fractional scale. The owner's display runs at 1.49, where the pieces of a frame can leave a seam one pixel wide. Pinned in Task 3, Step 4: every picture is taken at scale 1 and at scale 1.49.
- A line that is the same colour as what is next to it in the test, so that it cannot be seen. Pinned in Task 3, Step 1: frame, window content and backdrop are three loud, different colours, and pixels are read, not judged by eye.
- A stale cache of the SVG shows the previous theme. Pinned in Task 2, Step 5.
- The picture differs from what the owner sees on the real display. Pinned in Task 4, Step 3: the owner looks at the live nested window.

Read (do not write) the group `[org.kde.kdecoration2]` of `~/.config/kwinrc` and of `/etc/xdg/kwinrc` if they exist, to learn the key names KWin 6.8.2 uses for the decoration's plugin and theme.

- [x] **Step 2: Write `window.py`.** A PySide6 window, 480 × 320, with the title `amber-spike`, whose whole content is one flat colour given as `--fill <hex>` (default green `#00ff00`). `--maximized` opens it maximised. The backdrop of the nested KWin must be one known colour: note which colour it is with no window open.

- [x] **Step 4: Run it with `window.py`.** Expected: a window titled as KWin's nested output appears in the owner's session, and inside it the green test window with a decoration (Breeze's, since nothing is configured yet). - [x] **Step 5: Find a way to save a picture of the nested KWin's whole output as a PNG.** Try in this order and keep the first that works: (a) inside the nested session, KWin's `org.kde.KWin.ScreenShot2` on the nested bus, with `KWIN_SCREENSHOT_NO_PERMISSION_CHECKS=1` in the nested KWin's environment; (b) from the owner's session, `spectacle --background --activewindow --nonotify --output <file>` with the nested window active. Load the `ai-tools` skill before writing any script for this or for reading pixels. Save the picture as `tmp/spike-decoration/shots/baseline-breeze.png`.

### Task 2: A loud theme, to prove Aurorae is drawing

**Files:**
- Create: `tmp/spike-decoration/amber-spike/decoration.svg`, `tmp/spike-decoration/amber-spike/amber-spikerc`, `tmp/spike-decoration/amber-spike/metadata.desktop`, button files as needed
- Create: `tmp/spike-decoration/config/kwinrc`

- [x] **Step 1: Learn the theme format.** No Aurorae theme is installed on the machine, so the format is unverified. Read `/usr/share/kwin/aurorae/aurorae.qml` and the other QML files beside it for the element prefixes of `decoration.svg` (active, inactive, maximised, inner border, mask) and the names of the button files, and the `theme-description` file of the Aurorae repository at the tag of 6.8.2 for the rest. Keys the engine reads from the `rc` file include `BorderLeft`, `BorderRight`, `BorderTop`, `BorderBottom`, `PaddingLeft`, `PaddingRight`, `PaddingTop`, `PaddingBottom`, `TitleHeight`, `TitleEdgeTop`, `TitleEdgeBottom`, `TitleEdgeLeft`, `TitleEdgeRight`, `ButtonHeight`, `ButtonWidth`, `ActiveTextColor`, `InactiveTextColor`, `Animation`.

- [x] **Step 2: Write the loud theme.** `decoration.svg` is a frame of plain rectangles in magenta `#ff00ff` for the active window and a darker magenta `#800080` for the inactive one: no `rx` or `ry`, no stroke, no gradient, no filter. In the `rc` file: all four paddings 0 (no shadow), left, right and bottom border 0, title height 30, animation 0. Give the close button a plain square file so that the window can be closed; other buttons may be left out if the engine allows.

- [x] **Step 3: Install it and select it in the nested KWin only.** Copy the folder to `~/.local/share/aurorae/themes/amber-spike/`. Write `tmp/spike-decoration/config/kwinrc` with the keys found in Task 1, Step 1; they are expected to be `library=org.kde.kwin.aurorae` and `theme=__aurorae__svg__amber-spike` in `[org.kde.kdecoration2]` (unverified).

- [x] **Step 4: Run and picture.** Expected: the test window in the nested KWin has a magenta title bar. If it is not magenta, the theme is not in use: read the nested KWin's output for "Could not find decoration svg" and fix the theme before going on. Nothing learnt before this step passes counts as a finding about Aurorae.

- [x] **Step 5: Pin the cache.** Change the active colour in `decoration.svg` to `#ff00a0`, copy the folder again, start the nested KWin again, picture. Note whether the new colour shows at once, or only after `tmp/spike-decoration/cache/` is emptied. Use whatever was needed in every later step.

### Task 3: Corners and edges, pixel by pixel

**Files:**
- Modify: `tmp/spike-decoration/amber-spike/` (theme files)
- Create: `tmp/spike-decoration/shots/*.png`

- [x] **Step 1: Picture the loud theme with a floating window.** Frame magenta, content green, backdrop as noted in Task 1. Read the pixels of the picture:
  - *Corners:* at each of the four outer corners of the window, the corner pixel itself and its neighbours inwards are the frame's or the content's colour, with no backdrop colour and no blended colour. A blended or backdrop pixel inside the window's rectangle is a rounded corner.
  - *Edges:* walking inwards across the left, right and bottom edges at three places each, the colour goes from backdrop straight to content green. Any pixel of a third colour is a line. Across the top edge it goes from backdrop to magenta, and from magenta straight to green.
  - Count the colours in the whole picture: only backdrop, frame, content and the title's text and button should appear.

- [x] **Step 2: If a corner is not square or a line is found, find its source** before concluding. Try, one change at a time: a `mask` element in the SVG or none; inner-border elements or none; borders of 0 against borders of 1 px in the frame's colour; whether the line is KWin's and not Aurorae's (compare with the Breeze baseline picture of Task 1, and check the nested KWin's effects). Record each try and what it changed.

- [x] **Step 3: Repeat Step 1 for the other window states:** an inactive window (open a second window so that the first loses focus), a maximised window (`--maximized`; the title bar must meet the top and both sides of the output with no gap and no line), and a window that was maximised and restored.

- [x] **Step 4: Repeat Steps 1 and 3 at `--scale 1.49`**, the scale of the owner's display. A seam between the title bar and the content, or between pieces of the frame, counts as a line.

## Outcome — 2026-11-11

Done by the first clause: a window showed a square title bar with no border
line. What differed from the plan:

- The theme's format was read from <https://develop.kde.org/docs/plasma/aurorae/>;
  the `theme-description` file only points there.
- `--scale` changed nothing in the nested window, which always took the
  display's 1.49. Scale 1 was pictured with `--virtual`.
- On seeing the live window (Task 4, Step 3) the owner decided that a window
  has a window outline (D-25). One more try was made before the clean-up: a
  frame with a 1 px outline in a colour of its own, under three border
  sizes. Its findings are in the platform document.
