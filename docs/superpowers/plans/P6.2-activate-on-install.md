# P6.2 Activate on Install Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `scripts/install.sh --activate` installs the parts and selects every one of them, KWin's border size "Tiny" included, and `scripts/uninstall.sh` puts back every setting that activation changed.

**Architecture:** Activation writes a short, fixed list of keys into the owner's configuration files with `kwriteconfig6`, one key at a time. Before each write it appends a `set` line to the install record (D-135) holding the file, the group, the key, the earlier value (or that there was none) and the value written. Uninstall reads those lines in reverse order. It restores each key whose value is still the one activation wrote, and keeps and names a key the owner changed since. When a session bus is given, both scripts then ask KWin to reconfigure and tell running applications that the palette and the style changed. Which key selects the Union style, which value of KWin's `library` to write, and what `plasma-apply-colorscheme` writes are not verified, so Task 1 is a probe in throwaway configuration folders and the nested session. A spec runs the scripts in a throwaway home, as P6.1's does. Task 3 activates in the nested session. Task 4 is the owner's round trip on the real system.

**Tech Stack:** Bash 5, `kwriteconfig6` and `kreadconfig6` (KF 6.31), `dbus-send`, awk. Node 24 with `node:test` for the spec. The nested `kwin_wayland` 6.8.2 session (`tmp/check-colour-scheme/`, with `run.sh`, `in.sh` and `shot`), Dolphin, Kate, KWrite, Konsole, and the `image` tool. No new dependency.

**Spec:** `docs/product/roadmap.md` (row P6.2, and the notes under Step 6 for it). `docs/architecture/decisions.md` (D-24, D-135, D-136, D-137). `docs/product/vision.md` ("What success looks like": "uninstalling leaves the system as it was"). `docs/architecture/platform.md` ("Union" → "Tools and switches" and its "Unverified"; "Window decoration" on `BorderSize` and `library`; "Colour scheme" on `kdeglobals`, per-application schemes and `AccentColor`; "Konsole and Kate"). `docs/superpowers/plans/P6.1-install-and-uninstall.md` (the scripts and their spec, which this plan extends).

- Glossary words: **part**, **colour scheme**, **Union style**, **window decoration**, **terminal colours**, **editor theme**, **install record**, **known gap**. One new term, **activation**, goes into the glossary in Task 2, before any other document uses it: "What `install.sh --activate` does: selecting every part in the owner's settings, with each setting's earlier value kept in the install record so that uninstall puts it back." The **install record**'s entry gains "and every setting that activation changed".
- **`F`** is `$XDG_CONFIG_HOME` if it is an absolute path, and `$HOME/.config` otherwise (`amber_config` in `scripts/lib.sh`). `D` and `C` are as in P6.1.
- **The settings activation writes** (my call, D-138), each only when its value differs from what is there:

  | File | Group | Key | Value |
  |---|---|---|---|
  | `F/kdeglobals` | `General` | `AccentColor` | deleted, before the colour scheme is applied (Task 1: an accent colour replaces Amber's Selection) |
  | `F/kdeglobals` | the colour groups, `ColorScheme`, `ColorSchemeHash` | every key that `plasma-apply-colorscheme Amber` adds, changes or deletes | what the tool writes (Task 1: it derives `[Colors:Header][Inactive]` values and the hash, as System Settings does) |
  | `F/kdeglobals` | `KDE` | `widgetStyle` | `Union` |
  | `F/kdeglobals` | `KDE` | `unionStyle` | `amber` (verified in Task 1) |
  | `F/kwinrc` | `org.kde.kdecoration2` | `library` | `org.kde.kwin.aurorae.v2` (verified in Task 1) |
  | `F/kwinrc` | `org.kde.kdecoration2` | `theme` | `__aurorae__svg__amber` |
  | `F/kwinrc` | `org.kde.kdecoration2` | `BorderSize` | `Tiny` |
  | `F/kwinrc` | `org.kde.kdecoration2` | `BorderSizeAuto` | `false` |
  | the default Konsole profile (below) | `Appearance` | `ColorScheme` | `Amber` |
  | `F/katerc` and `F/kwriterc` | `KTextEditor Renderer` | `Color Theme` | `Amber` |
  | `F/katerc` and `F/kwriterc` | `KTextEditor Renderer` | `Auto Color Theme Selection` | `false` |

  A group name with `][`, such as `Colors:Header][Inactive`, is passed to `kwriteconfig6` as two `--group` options. The colour scheme is applied with `QT_QPA_PLATFORM=offscreen plasma-apply-colorscheme Amber`, with `XDG_DATA_HOME` pointing at `D`; activation reads every key of `kdeglobals` before and after it, and writes a `set` line for each key that changed. The `set` lines of that run are written after the tool, since its changes are not known before (changed after Task 1, which found that the tool writes values the file does not hold).
- **The default Konsole profile** (my call, D-140). If `DefaultProfile` in `[Desktop Entry]` of `F/konsolerc` names a file that exists in `D/konsole/`, activation sets the key in that file. Otherwise activation writes `D/konsole/Amber.profile` (`[General]` `Name=Amber`, `Parent=FALLBACK/`; `[Appearance]` `ColorScheme=Amber`) as a `file` line of the record, and sets `DefaultProfile=Amber.profile`. An `Amber.profile` that exists and that the record does not list is refused, as P6.1 refuses any file Amber did not write.
- **How a setting is written and recorded** (my call, D-138). Reading uses a small awk reader in `scripts/settings.sh`, since `kreadconfig6` cannot tell an empty value from a missing key. Writing and deleting use `kwriteconfig6 --file <absolute path>` (`--delete` to remove a key). The record line is written before the key, so that an activation killed halfway can still be undone. It is tab-separated:

  ```text
  set<TAB><file><TAB><group><TAB><key><TAB><before><TAB><after>
  ```

  `<before>` and `<after>` are `=` followed by the value, or `-` when the key is missing (changed in Task 2: a deleted `AccentColor` needs `-`). When activation creates a configuration file, a `created <file>` line comes first. Uninstall removes that file only if, once its keys are restored, it holds no key.
- **What uninstall does with the colour scheme** (changed after the final review): its keys are `cset` lines, restored together while `ColorScheme` and `ColorSchemeHash` hold what activation left (a `scheme` line), and all kept, with one `kept` line, otherwise. With no session bus given, `plasma-apply-colorscheme` runs with `XDG_RUNTIME_DIR` unset and `DBUS_SESSION_BUS_ADDRESS=unix:path=/nonexistent`, since libdbus falls back to `$XDG_RUNTIME_DIR/bus`. A later activation updates the `<after>` of a key already recorded.
- **What uninstall does with a setting** (my call, D-139). It works through the `set` lines in reverse order. If the key's value is still `<after>`, it puts `<before>` back (or deletes the key). If the owner changed it since install, uninstall leaves the owner's value and prints `kept <file> [<group>] <key>=<value>: changed since install`. It prints one line per file it restored. D-136's report runs after the restore, so a setting that selected Amber before install is still named.
- **Install over an earlier install keeps the activation.** The `set` and `created` lines of the old record are carried into the new one, and no setting is restored. A second `--activate` records only keys that it changes now. So uninstall always goes back to the values from before the first activation.
- **Without `--activate`, install writes nothing under `F`**, and D-136 holds as before.
- **Telling running programs** (my call, D-138, as Task 1 found). Only when `DBUS_SESSION_BUS_ADDRESS` is set: after activation, `dbus-send --session --type=signal /KWin org.kde.KWin.reloadConfig` (the palette is announced by `plasma-apply-colorscheme` itself); after a restore, that and `dbus-send --session --type=signal /KGlobalSettings org.kde.KGlobalSettings.notifyChange int32:0 int32:0` (palette). A failure is ignored. KWin's `reconfigure` method did not apply a border size, and the style signal did not change an open application's style, so neither is sent. The scripts then print that applications show the Union style, and Konsole, Kate and KWrite their parts, when they start again.
- **Arguments.** `install.sh` takes `--activate` or `--help`, and one of them at most. Any other argument, or `uninstall.sh` with any argument but `--help`, gives exit 2. Exit codes are otherwise P6.1's.
- **A refusal writes no setting.** All of P6.1's checks, and the `Amber.profile` check, run before any file or key is written.
- **Never change the owner's system settings** (D-24, D-137). An agent runs activation only with `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_CACHE_HOME` set to folders under `tmp/`, and with `DBUS_SESSION_BUS_ADDRESS` unset or set to the nested session's bus. At the start and end of Tasks 1 and 3, `sha256sum ~/.config/{kdeglobals,kwinrc,konsolerc,katerc,kwriterc} ~/.local/share/konsole/*.profile` gives the same result. Only Task 4 writes to the real configuration, and the owner runs it.
- **Anti-goals:** activation draws nothing new. It must select Amber's parts and not leave one of them on Breeze. Task 3's shot is read with `image greys --token-blends` and `image lines --blends`; a cool grey or hairline that P5.3's findings do not list means a part is not selected. "Tiny" is the border size that leaves only the window outline (D-25).
- **Stop and ask the owner** if any of these happens:
  - no configuration key selects the Union style for the whole system (Task 1);
  - KWin does not load the decoration from the keys of the table (Task 1);
  - the applications do not show a part after activation, with no setting changed by hand (Task 3);
  - after uninstall, a setting activation wrote is not as it was before (Task 3 or Task 4).
