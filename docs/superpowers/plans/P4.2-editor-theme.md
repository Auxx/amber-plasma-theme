# P4.2 Editor Theme Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Generate `parts/editor-theme/Amber.theme` from the tokens, show it in Kate in the nested session, and match it to the prototype's editor sample.

**Architecture:** A hand-written table, `parts/editor-theme/styles.json`, gives each text style and each editor colour of a KSyntaxHighlighting theme a token, as `keys.json` does for the terminal colours (D-118). A new library, `tools/src/lib/editor-theme.mjs`, turns the table and the tokens into the theme's JSON. `generate editor-theme` prints it and writes it with `--write`, and a spec fails when the committed file is stale (D-92). The `sample` tool gets two new commands. `sample editor` prints the prototype's code as plain text. `sample compare-editor` reads the HTML that `ksyntaxhighlighter6` writes for that text with the Amber theme and names every run whose colour differs from the prototype's token. So "matches the sample" is checked by the same library Kate uses, with no screenshot. Task 3 then looks at Kate itself.

**Tech Stack:** Node 24 ES modules with `node:test`; the `tokens`, `colour`, `generate`, `sample`, `browser` and `image` tools; `ksyntaxhighlighter6` 6.31.0 (KF6 SyntaxHighlighting, `kf6-syntax-highlighting-6.31.0-1.fc45`); Kate 26.08.2 in the nested `kwin_wayland` session (`tmp/check-colour-scheme/`, with `run.sh`, `in.sh` and `shot`), whose `XDG_CONFIG_HOME` is `tmp/check-colour-scheme/config`. No new dependency.

**Spec:** `docs/product/roadmap.md` (row P4.2; the note under Step 4), `docs/architecture/design-language.md` ("Editor theme": its "no line" rule and the mapping left to P4.2), `prototype/tokens.css` (the editor tokens), `prototype/contrast-pairs.json`, `prototype/samples.html` and `samples.css` (the editor sample), `docs/architecture/accessibility.md` (rule 3), `docs/architecture/overview.md` (the parts table: `.theme` (JSON) in `org.kde.syntax-highlighting/themes/`), `docs/architecture/platform.md` ("Konsole and Kate"), `docs/architecture/decisions.md` (D-53, D-56, D-79, D-82, D-83, D-92, D-118), `docs/architecture/tooling.md`.

## Global Constraints

- Branch `feat/p4.2-editor-theme` from `master`; this plan file is committed on it in Task 1.
- Glossary words, British spelling: **editor theme** (never "colour theme", which is Kate's name for its setting), **syntax colour**, **gutter** (never "icon border", except when naming Kate's key `IconBorder`), **current line**, **text selection**, **sample**, **token**. One new term goes into the glossary in Task 1, after "Text selection", before any other file uses it:
  - **Search highlight**: the tone Kate puts behind every match of a search. _Avoid_ "find highlight".
- **The theme's keys** (verified 2026-11-13 from the enums `TextStyle` and `EditorColorRole` in `libKF6SyntaxHighlighting.so.6.31.0`, in this order):
  - 31 text styles: `Normal`, `Keyword`, `Function`, `Variable`, `ControlFlow`, `Operator`, `BuiltIn`, `Extension`, `Preprocessor`, `Attribute`, `Char`, `SpecialChar`, `String`, `VerbatimString`, `SpecialString`, `Import`, `DataType`, `DecVal`, `BaseN`, `Float`, `Constant`, `Comment`, `Documentation`, `Annotation`, `CommentVar`, `RegionMarker`, `Information`, `Warning`, `Alert`, `Error`, `Others`.
  - 28 editor colours: `BackgroundColor`, `TextSelection`, `CurrentLine`, `SearchHighlight`, `ReplaceHighlight`, `BracketMatching`, `TabMarker`, `SpellChecking`, `IndentationLine`, `IconBorder`, `CodeFolding`, `LineNumbers`, `CurrentLineNumber`, `WordWrapMarker`, `ModifiedLines`, `SavedLines`, `Separator`, `MarkBookmark`, `MarkBreakpointActive`, `MarkBreakpointReached`, `MarkBreakpointDisabled`, `MarkExecution`, `MarkWarning`, `MarkError`, `TemplateBackground`, `TemplatePlaceholder`, `TemplateFocusedPlaceholder`, `TemplateReadOnlyPlaceholder`.
- **File format** (unverified until Task 2 Step 5, which loads the file through the library): one JSON object with these keys in this order:
  - `metadata`: `{ "copyright": ["SPDX-FileCopyrightText: 2026 Aleksandr 'Aux' Ivanov"], "license": "SPDX-License-Identifier: MIT", "name": "Amber", "revision": 1 }`.
  - `text-styles`: each style is `{ "text-color", "selected-text-color", "bold": false, "italic": false, "underline": false, "strike-through": false }`. Both colours are the token's hex: a syntax colour keeps its hue in a text selection (D-82).
  - `editor-colors`: key → hex.
  - `custom-styles`: `{}`.

  Keys appear in the order above. Hex is `#rrggbb`, lower case, from `srgb8`. Written by `JSON.stringify(theme, null, 4)` plus one newline. JSON has no comments, so the file has no "do not edit" line (my call). The up-to-date spec catches a hand edit.
- **No bold, no italic** (my call): Amber is flat, and the prototype draws every style upright and regular.
- **The table** (`styles.json`, my call, recorded as D-121 in Task 4). Every key takes a token; no literal colour:

  | Text styles | Token |
  |---|---|
  | `Normal`, `Variable`, `Operator`, `Others` | `text` |
  | `Keyword`, `ControlFlow`, `DataType`, `Attribute` | `syntax-keyword` |
  | `Function`, `BuiltIn`, `Information` | `syntax-function` |
  | `Extension`, `Annotation`, `CommentVar` | `syntax-type` |
  | `String`, `VerbatimString`, `SpecialString`, `Char`, `SpecialChar` | `syntax-string` |
  | `DecVal`, `BaseN`, `Float`, `Constant`, `Alert`, `Error` | `syntax-number` |
  | `Preprocessor`, `Import`, `RegionMarker`, `Warning` | `syntax-preprocessor` |
  | `Comment`, `Documentation` | `syntax-comment` |

  Why: `ksyntaxhighlighter6 -t "Breeze Dark" --syntax-trace format` on the sample's code (2026-11-13) shows how Kate's C++ highlighting splits it. `static`, `const` and `int` are `DataType`. `constexpr` is `Keyword`. `for`, `if`, `continue` and `return` are `ControlFlow`. `QDir`, `QString` and `QFileInfo` are `Extension`. `u'.'` is `Char`. Punctuation is `Operator`. The prototype draws all the keywords alike, the Qt classes as types and punctuation as text, and this table follows it.

  | Editor colours | Token | Why |
  |---|---|---|
  | `BackgroundColor`, `TemplateBackground` | `editor` | |
  | `TextSelection`, `TemplateFocusedPlaceholder` | `editor-selection` | |
  | `CurrentLine`, `CodeFolding`, `TemplatePlaceholder` | `editor-current-line` | |
  | `SearchHighlight`, `ReplaceHighlight` | `editor-search` (new, below) | |
  | `BracketMatching` | `tone-4` | a tone above the current line, under text |
  | `IconBorder`, `TemplateReadOnlyPlaceholder` | `editor-gutter` | |
  | `LineNumbers`, `TabMarker`, `MarkBreakpointDisabled` | `text-dim` | |
  | `CurrentLineNumber` | `text` | |
  | `IndentationLine`, `WordWrapMarker` | `editor` | hidden: a hairline in the code's own tone draws nothing |
  | `Separator` | `editor-gutter` | hidden: the line between gutter and code |
  | `SpellChecking`, `MarkBreakpointActive`, `MarkError` | `syntax-number` | |
  | `ModifiedLines`, `MarkBreakpointReached`, `MarkWarning` | `syntax-preprocessor` | |
  | `SavedLines` | `syntax-string` | |
  | `MarkBookmark` | `syntax-function` | |
  | `MarkExecution` | `syntax-type` | |

- **One new token, `editor-search`** (my call for the starting value): the search highlight must stand apart from the text selection and the current line, and carry every syntax colour. `text-selection` (`#605239`) would fail: the syntax colours measure 3.0 to 3.7:1 on it (measured 2026-11-13). The starting value is OKLCH 37 % 0.05 125, a dark olive. It is as dark as the text selection, so the syntax colours pass, and its hue differs from the selection's gold. Chroma 0.05 keeps it a colour, not a grey. Task 1 puts two **candidates** beside it on the samples page, for the owner in Task 3: OKLCH 37 % 0.05 80 (gold, a stronger text selection) and `tone-4`.
- **Contrast pairs** (accessibility rule 3, D-53). Every text-style token has a pair on `editor`, `editor-current-line`, `editor-selection` and `editor-search`, minimum 4.5. The comment's pairs on `editor-selection` and `editor-search` keep the floor of 4 (D-82). `text` also gets a pair on `tone-4`, minimum 4.5, for bracket matching. Every gutter key's token (`LineNumbers`, `CurrentLineNumber`, `ModifiedLines`, `SavedLines`, `Mark*`) has a pair on `editor-gutter`, minimum 4.5 for line numbers and 3 for marks (WCAG 1.4.11). `editor-search` gets a pair on `editor` with the floor 1.1 that `editor-selection` has, and one on `editor-selection`, also 1.1, so that the two are told apart. A spec checks every one of these (Task 1), and `node tools/src/bin/tokens.mjs pairs` passes.
- **Fail loudly** (tooling rule 7): a table with a missing or unknown key, an unknown token, or a token whose alpha is below 1 is refused. Each problem is named on its own line, starting with `text-styles.<key>` or `editor-colors.<key>`. Nothing is written.
- **Never change the owner's system settings.** At the start and end of Task 3, `sha256sum ~/.config/katerc ~/.config/kwriterc ~/.config/kdeglobals` gives the same result, and `~/.local/share/org.kde.syntax-highlighting` does not exist. Kate runs only in the nested session. That session finds the theme through a link `tmp/check-colour-scheme/data/org.kde.syntax-highlighting/themes/Amber.theme` → the repository's file. Choosing Amber in the nested Kate's settings writes only under `tmp/check-colour-scheme/config/`. Both facts are unverified and tested first. Installing the file is P6.1's job.
- Paths stay inside the repository. `generate editor-theme --write` writes only `parts/editor-theme/Amber.theme`. Highlighted HTML and shots stay in `tmp/` and are not committed.
- Anti-goals: the theme's colours are tokens, and the hairlines Kate can draw (`IndentationLine`, `WordWrapMarker`, `Separator`) take the tone they sit on. Task 3 turns each on in the nested Kate and checks with `image lines`.
- **Stop and ask the owner:** if Kate does not find the theme through `XDG_DATA_DIRS`; if a hairline still shows when it takes its surface's tone; or when the comparison finds runs that Kate's highlighting cannot colour as the sample does (expected: see Review Focus 1).

## Review Focus

1. **The sample promises more than Kate's highlighting does.** On 2026-11-13, Kate's C++ highlighting gave the function names (`countFiles`, `entryInfoList`, `fileName`, `startsWith`) and the constant `kLimit` the `Normal` style. It gave `"amber.h"` the `Import` style (the preprocessor colour), where the sample has a string. No table fixes these. Expected: `sample compare-editor` names exactly these runs. The owner chooses whether the sample is changed to what Kate draws, or the runs are kept as a known gap. Pinned by `names the runs Kate colours differently` (Task 2), and decided in Task 3 Step 4.
2. **A stale committed file**: a token changes and `Amber.theme` is not regenerated. Expected: the tests fail and name the command. Pinned by `Amber.theme is up to date` (Task 2).
3. **A hairline drawn by Kate**: an indentation line, the word wrap marker, the separator beside the gutter, or a modified-lines bar 1 or 2 px wide. Expected: the three hidden keys equal their surface's hex (spec `hides the hairlines`, Task 1). Task 3 turns each on and runs `image lines`. A modified-lines bar that turns out to be a hairline goes to the owner.
4. **A token used without a pair**, such as a mark colour on the gutter. Expected: the spec `every token has its pairs` fails and names the key and the background. Pinned in Task 1.
5. **The highlighter's HTML in a form the comparison does not read** (a `font-weight` in the style, an entity, a span across two lines). Expected: `compare-editor` exits 1 and names the form, rather than counting a run as matching. Pinned by `refuses a style it cannot read` (Task 2).
