# P1.5 Gallery: navigation, views and popups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The gallery page `prototype/gallery.html` gains four families. "Navigation" has tabs and items. "Views" has header sections, plus a live tree view and a live table view. "Popups" has menu items, plus an open menu, an open combo box list and a tooltip. "Dialog" has one dialog. Each state sits beside the others and reacts to the pointer and the keyboard. Selected items and tabs carry the block marker, and the window shell's selected items gain it too. Beside them are candidates for the selected item and for the popup's shadow, each with its measured contrast.

**Architecture:** The pattern of P1.3 and P1.4 continues. The new tones become tokens with contrast pairs. `widgets.css` writes each state rule for the pseudo-class and its forced class together. `prototype-gallery.spec.mjs` checks every state's tones in Chrome, and checks that a live control matches its forced copy. The block marker is a gradient in `var(--marker)`, `var(--marker-width)` wide. It is not a border, so it is not a hairline. A popup is drawn like a small inactive window. Its shadow is the same gradient as the window's in `window.css`, shared through one rule, so the gallery links `window.css`. The tree view uses `<details>` and `<summary>`, so it opens and closes with no script. Selecting an item or a tab needs a script that sets a class, which D-48 forbids. So selected copies are forced, and the live controls react to hovering and focus only.

**Tech Stack:** HTML and CSS opened as `file://` (D-35); Node 24 ES modules, `node:test`, `node:assert/strict`; the existing `tokens.mjs`, `prototype-check.mjs` and `browser.mjs` (playwright-core with the installed Chrome, D-46). No new dependency, and no new script.

**Spec:** `docs/product/roadmap.md` (P1.5, which is done "as P1.3": each state is shown side by side and reacts to the pointer and the keyboard), `docs/architecture/design-language.md` (Principles, Surfaces, Widgets, Shadow), `docs/architecture/accessibility.md` (rules 1, 2 and 4), `docs/architecture/decisions.md` (D-2, D-3, D-4, D-21, D-36, D-48, O-3), `docs/architecture/platform.md` (the open question on popup shadows, P3.8), `docs/product/glossary.md` (Block marker, Shadow, Hairline, Widget states). For the gallery's markup, its spec and its candidates, see `docs/superpowers/plans/P1.4-gallery-toggles-and-ranges.md` and the P1.3 plan.

## Global Constraints

- Branch `feat/p1.5-gallery-navigation-views-and-popups`. This file is committed on it.
- Use the glossary's words and British spelling. The new terms go into the glossary first (Task 1, Step 1).
- Every constraint of P1.3 and P1.4 still holds:
  - no rounded corner, no hairline and no cool grey;
  - every colour comes from `prototype/tokens.css`, except in a candidate's `style`;
  - no `<style>`, no `<hr>` and no at-rule;
  - a `style` attribute only sets custom properties;
  - controls are reset with `appearance: none`, `border: 0`, `border-radius: 0`, `outline: none` and `font: inherit`;
  - `gallery.js` stays as it is, with no new script.
- **No line anywhere.** A tree has no branch lines. A table has no grid lines. A header has no dividers between its sections. A menu separator is an 8 px gap, with no line and no band of tone. A dialog has no line above its buttons. Task 2 teaches the rendered check to find a line drawn as a thin filled box.
- New tokens and starting values (my call; the owner reviews them in P1.7):

  | Token | Value | Why |
  |---|---|---|
  | `--selected` | `var(--tone-3)` | a selected item, as the design language already says |
  | `--marker-width` | `3px` | the block marker; D-21 asks for at least three pixels |
  | `--popup` | `var(--tone-3)` | a menu, a combo box list or a tooltip: one tone above the tone 2 surface |
  | `--popup-shadow-size` | `12px` | how far a popup's shadow fades to nothing; half the window's |
  | `--popup-shadow-offset` | `4px` | how far the shadow sits below the popup ("offset downwards") |

  The popup's shadow takes its colour from `--shadow`, black at 50 %, as an inactive window's does.
- The tones of every state (my call; Tasks 3 to 5 test them by name). Each cell gives the values read, in the order of "Reads":

  | Widget | Reads | At rest | Hovered | Focused | Pressed | Selected, checked or sorted | Disabled |
  |---|---|---|---|---|---|---|---|
  | Tab, on a tone 0 tab bar | background / text / `--marker` | transparent / text / transparent | tone-1 / text / transparent | well-focus / text / transparent | — | selected: tone-2 / text / accent | transparent / text-dim / transparent |
  | Item, on tone 2 | background / text / `--marker` | transparent / text / transparent | tone-3 / text / transparent | raised-focus / text / transparent | — | selected: selected / text / accent | transparent / text-dim / transparent |
  | Header section | background / text | transparent / text-dim | tone-3 / text | — | tone-1 / text | sorted: transparent / text | — |
  | Menu item, in a popup | background / text / `--mark` | transparent / text / transparent | tone-4 / text / transparent | tone-4 / text / transparent | — | checked: transparent / text / accent | transparent / text-dim / transparent |

  Precedence works as in P1.3: pressed wins over focused, and focused over hovered. A disabled widget never changes. More rules (my call):
  - **A selected item when hovered** goes to tone 4 and keeps its marker. When focused, it takes raised focus and keeps its marker.
  - **A selected tab** stays tone 2 when hovered, because it joins the page below it. When focused, it takes well focus and keeps its marker.
  - **A checked menu item** is tone 4 when hovered, with its tick in accent.
  - **Where the marker sits.** An item's marker is on its leading edge (left). A tab's marker is on its top edge, so that the selected tab still joins its page.
  - **Why the focused tones.** A tab's focused tone is well focus, which is accent 16 % over tone 1, its hovered tone. An item's is raised focus, accent 30 % over tone 4. This follows the rule that the focused tone is accent mixed over the tone a widget has when hovered.
  - **A menu item's keyboard highlight is its hovered tone.** Qt does not tell the two apart.
  - **Secondary columns.** An item may hold dim secondary text (`.item-detail`). On a focused item it becomes text, because dim text on raised focus measures 2.58:1 (finding below).
- Sizes (my call):
  - a tab is 28 px high with 12 px padding;
  - an item and a menu item are 26 px high;
  - a menu item has a 28 px column for its tick on the left, and its shortcut in dim text on the right;
  - a popup has 4 px padding at the top and the bottom;
  - a tooltip has 4 × 8 px padding and is at most 240 px wide;
  - a tree indents 20 px a level, and its chevron is a 16 px glyph in dim text that turns 90° when open;
  - a header section is 26 px high, and its sort arrow is a 16 px glyph in `currentColor`.
- New contrast pairs. 45 pairs become 53:
  - `text` also on `selected`, `popup` (+2; 10.58, 10.58).
  - `text-dim` also on `selected`, `popup` (+2; 5.34, 5.34): secondary columns, shortcuts.
  - `accent` also on `selected`, `well-focus` (+2; 6.54, 6.13): the block marker on a selected item and on a focused selected tab (rule 2). The marker on a hovered or focused selected item is already measured: `accent on tone-4` 5.63 and `accent on raised-focus` 3.16.
  - New: `selected on tone-2, tone-1`, minimum 1.1 (1.17, 1.28). This is a floor (my call), not a WCAG rule. The marker carries rule 2's 3:1, and the tone groups the item.
- Candidates (my call). Each figure varies one token from the starting values:

  | Group | Figure | Override | Ratios printed |
  |---|---|---|---|
  | Selected item | Start, tone 3 and a 3 px marker | none | accent on selected 6.54, selected on tone 2 1.17, dim text on selected 5.34 |
  | | No marker | `--marker-width: 0px` | 1.17, 5.34 |
  | | Lighter, tone 4 | `--selected: var(--tone-4)` | 5.63, 1.36, 4.60 |
  | Popup | Start, with a shadow | none | dim text on popup 5.34 |
  | | No shadow | `--popup-shadow-size: 0px` | 5.34 |

  The pairs printed are `accent on selected`, `selected on tone-2` and `text-dim on selected`, and then `text-dim on popup`. A "No marker" figure prints no marker ratio. This adds 5 figures and 10 ratios, so the gallery shows 28 figures and 62 ratios.
- Findings for the documents, measured on 2026-11-11:
  - **Dim text on raised focus measures 2.58:1**, which fails rule 1. So a focused item shows its secondary columns in text.
  - **Without the marker, a selected item looks like a hovered one.** Both are tone 3, and the selection is shown by tone alone at 1.17:1. With the marker, the selection reaches 6.54:1. The marker is therefore part of selection, not an option. D-21 changes from "may carry" to "carries" (Designer). The owner sees both in P1.7.
- **Popup shadows are unverified on the platform.** Whether Union draws a shadow under a menu in a Qt Widgets application is an open question for P3.8 (platform document). The design language already gives popups a shadow, so the prototype draws one, and the "No shadow" candidate shows the look if P3.8 says no. That is D-49 (Designer), in Task 7.

## Review Focus

- **A line that slips past the check.** A menu separator, a header divider or a tree branch line drawn as a 1 or 2 px filled box is a hairline that `renderedOffences` does not see today. This is pinned by Task 2's `finds a line drawn as a box`. Every page then runs the new rule through `breaks no anti-goal in any state` and `browser check`.
- **The keyboard walk across live areas.** The walk used to stop at the first stop outside a state cell, which was the scroll area. The new families come after it, so their tabs, items and menu items would never be walked. The walk now runs on to the candidates, and allows only the listed live stops (Task 3, `takes the keyboard in order`).
- **Chrome's own drawing.** Watch for the triangle of a `<summary>`, a button's focus ring on a tab or a menu item, and the grey selection of a native list. These are pinned by `draws no native marker on the tree` (Task 4) and by the anti-goal check in every live state.
- **States that combine.** A hovered or focused selected item must keep its marker, and a selected tab must not lighten when hovered. A disabled item that is hovered must not change. These are pinned by the extended `keeps the precedence of states` (Tasks 3 and 5).
- **A tooltip that never shows, or never hides.** It must show when its anchor is hovered and when the anchor holds keyboard focus, and hide again when the pointer leaves. This is pinned by `shows a tooltip on hover and on focus` (Task 5).
