# P4.1 Terminal Colours Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Generate `parts/terminal-colours/Amber.colorscheme` from the tokens, show it in Konsole in the nested session, and match it to the prototype's terminal sample.

**Architecture:** A hand-written table, `parts/terminal-colours/keys.json`, gives every colour key of a Konsole colour scheme a token, as `roles.json` does for the colour scheme (P2.1). A new library, `tools/src/lib/terminal-colours.mjs`, turns the table and the tokens into the file's text; `generate terminal-colours` prints it and writes it with `--write`, and a spec fails when the committed file is stale (D-92). A new tool, `sample`, reads the prototype's terminal sample from `prototype/samples.html` and prints it with ANSI escape sequences, so that Konsole draws the same text in the same colours as the browser. Task 3 runs it in Konsole in the nested session and compares the two pictures by token.

**Tech Stack:** Node 24 ES modules with `node:test`; the `tokens`, `colour`, `generate`, `browser` and `image` tools; Konsole 26.08.2 in the nested `kwin_wayland` session of P2.3 to P3.9 (`tmp/check-colour-scheme/`, with `run.sh`, `in.sh` and `shot`). No new dependency.

**Spec:** `docs/product/roadmap.md` (row P4.1; the note on Konsole's pane header under Step 3), `prototype/tokens.css` (the terminal colours), `prototype/contrast-pairs.json`, `prototype/samples.html` (the terminal sample), `docs/architecture/overview.md` (the parts; generated parts are committed), `docs/architecture/platform.md` ("Konsole and Kate"; "Colour scheme" for the nested session), `docs/architecture/decisions.md` (D-12, D-20, D-53, D-78, D-80, D-81, D-92, D-116), `docs/architecture/tooling.md`.

## Global Constraints

- Branch `feat/p4.1-terminal-colours` from `master`; this plan file is committed on it in Task 1.
- Glossary words, British spelling: **terminal colours** for the file (never plain "colour scheme"), **ANSI colour**, **bright** (Konsole's "Intense" only when naming its keys), **sample**, **token**. Two new terms go into the glossary in Task 1 before any other file uses them:
  - **Faint**: text a program asks to be drawn dim (SGR 2). Konsole's word, kept since Amber has no other; _avoid_ "dim" for it, which is the `text-dim` token.
  - **Pane header**: the title strip Konsole draws above each pane of a split view.
- **File format** (verified 2026-11-13 from the colour schemes built into `libkonsoleprivate.so.26.08.2`, among them Breeze): INI groups `[Background]`, `[BackgroundFaint]`, `[BackgroundIntense]`, `[Color0]` … `[Color7]`, each with `Faint` and `Intense` variants, `[Foreground]`, `[ForegroundFaint]`, `[ForegroundIntense]`, `[General]`. A colour group holds one line `Color=r,g,b` in decimal (from `srgb8`). Groups are sorted in code-unit order (`Array.prototype.sort()` with no comparer), as Konsole's own files are. `[General]` holds, sorted: `Blur=false`, `ColorRandomization=false`, `Description=Amber`, `Opacity=1`, `Wallpaper=` (empty). One blank line between groups; the file ends with one newline.
- **Header** (my call), as `Amber.colors`':

  ```text
  # SPDX-FileCopyrightText: 2026 Aleksandr 'Aux' Ivanov
  # SPDX-License-Identifier: MIT
  # Generated from prototype/tokens.css and parts/terminal-colours/keys.json.
  # Do not edit: run node tools/src/bin/generate.mjs terminal-colours --write
  ```

- **The table** (`keys.json`, my call, recorded as D-118 in Task 4). Every key takes a token; no literal colour, no rule:

  | Key | Token |
  |---|---|
  | `Background`, `BackgroundFaint`, `BackgroundIntense` | `terminal` |
  | `Foreground` | `terminal-text` |
  | `ForegroundFaint` | `text-dim` |
  | `ForegroundIntense` | `ansi-bright-white` |
  | `Color0` … `Color7` | `ansi-black`, `ansi-red`, `ansi-green`, `ansi-yellow`, `ansi-blue`, `ansi-magenta`, `ansi-cyan`, `ansi-white` |
  | `Color0Intense` … `Color7Intense` | the `ansi-bright-*` of the same colour |
  | `Color0Faint` … `Color6Faint` | the normal colour itself |
  | `Color7Faint` | `text-dim` |

  Why: a faint colour that is the normal one mixed towards the background, as Breeze does, would be a colour no token holds and no contrast pair checks. Faint white and the faint foreground fall to dim text, which reaches 4.5:1; the normal colours already sit at 3.5:1 (D-81).
- **Contrast pairs:** no new token. Every key other than the backgrounds and `Color0*` uses a token that already has a pair on `terminal`; a spec checks this (Task 1), and `node tools/src/bin/tokens.mjs pairs` passes. ANSI black is exempt (D-53).
- **Fail loudly** (tooling rule 7): a table with a missing or unknown key, an unknown token, or a token whose alpha is below 1 is refused, every problem named on its own line starting with the key. Nothing is written.
- **Never change the owner's system settings.** `sha256sum ~/.config/konsolerc ~/.local/share/konsole/*` gives the same result at the start and end of Task 3. Konsole runs only in the nested session, which finds the file through a link `tmp/check-colour-scheme/data/konsole/Amber.colorscheme` → the repository's file, and takes it with `-p ColorScheme=Amber` on its command line. Both are unverified and tested first in Task 3. Installing the file is P6.1's job.
- Paths stay inside the repository. `generate terminal-colours --write` writes only `parts/terminal-colours/Amber.colorscheme`. Shots stay in `tmp/` and are not committed.
- Anti-goals: the file's colours are tokens, so it brings no cool grey. The terminal area draws no line or corner of its own; Task 3 checks both in the shots.
- **Stop and ask the owner** if Konsole does not find the file through `XDG_DATA_DIRS`, if `-p` is not taken, or if the pane header stays a cool dark with Amber's terminal colours (then it is a known gap, the owner's to accept).

## Review Focus

1. **A stale committed file**: a token changes and `Amber.colorscheme` is not regenerated. Expected: the tests fail and name the command. Pinned by `Amber.colorscheme is up to date` (Task 2).
2. **Bright and normal swapped**: `Color1` given `ansi-bright-red`. Expected: caught, since `mc` and every prompt would look wrong. Pinned by `uses the sample's tokens for each ANSI colour` (Task 2), which checks each `ColorN` and `ColorNIntense` against the token that the sample's class `ansi-<name>` uses in `prototype/samples.css`.
3. **A token added to the table without a pair**, such as a new faint colour. Expected: the spec `every key has a pair on the terminal` fails and names the key. Pinned in Task 1.
4. **A span the escape printer does not know** (a new class in the sample, such as `on-white`). Expected: `sample terminal` exits 1 and names the class, rather than printing it in the default colour, which would make the comparison pass by accident. Pinned in Task 2.
5. **Konsole's pane header and margins**: the strip above a split pane and the margin around the text may not take `Background`. Expected: Task 3 shoots a split view and reads both with `image greys`; a cool grey there is either fixed by a key or brought to the owner.
