# P5.3 Glow, Shadow and Window States Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Generate the window glow of the active window and the shadow of an inactive one into the decoration's frame, from the tokens. Check maximised and tiled windows. Match all of it to the prototype in the nested KWin.

**Architecture:** P0.6 showed that an Aurorae theme draws a shadow or glow as gradients in the frame's edge and corner elements, inside the room that `Padding*` keeps around the window. Two things are still unverified (platform, "Unverified"). One is whether Aurorae draws the prototype's eased fade. The other is how the shadow, whose fade starts inside the window, can join at the corners. So Task 1 is a probe: hand-edited copies of the theme in `tmp/`, which decide the corner geometry before anything is generated. Task 2 gives the prototype a "Windows" family on known backdrops. It also gives the `image` tool a command that recovers a light's alpha from a shot and compares it with the tokens. Task 3 teaches `decoration.mjs` the padding, the gradients and the `Shadow` key. Task 4 checks every window state in KWin at scales 1 and 1.49, and Task 5 writes it down.

**Tech Stack:** Node 24 ES modules with `node:test`; the `tokens`, `generate`, `browser` and `image` tools; KWin and Aurorae 6.8.2 (`kwin-6.8.2-3.fc45`, `aurorae-6.8.2-1.fc45`) in the nested `kwin_wayland` session (`tmp/check-colour-scheme/`, with `run.sh`, `in.sh`, `in-x11.sh`, `shot`, `xkeys.py`, and P5.1's KWin scripts for placing windows). Its `XDG_CONFIG_HOME` is `tmp/check-colour-scheme/config`. No new dependency.

**Spec:** `docs/product/roadmap.md` (row P5.3, and the notes under Step 5 that P5.1 and P5.2 left for it). `docs/architecture/design-language.md` ("Window decoration", "Shadow"). `prototype/tokens.css` (`--glow`, `--glow-size`, `--shadow`, `--shadow-size`, `--shadow-inset-*`). `prototype/window.css` (`--light-fade` and `.window::before`). `docs/architecture/platform.md` ("Window decoration", "Amber's frame — P5.1", "Amber's window buttons — P5.2", its "Unverified" table, and spike P0.6). `docs/architecture/decisions.md` (D-4, D-25, D-26, D-59 to D-63, D-125, D-126, D-128 to D-130). `docs/architecture/tooling.md`.

## Global Constraints

- Branch `feat/p5.3-glow-shadow-and-window-states` from `master`. This plan file is committed on it in Task 1.
- Glossary words: **window glow**, **shadow**, **window outline**, **window decoration** ("decoration"), **title bar**, **window button**, **active** and **inactive** for windows, **tone**, **token**, **breach**, **known gap**. "Maximised" and "tiled" are KWin's words and need no entry. "Light" names the window glow or the shadow, whichever a window has, as `window.css` does. It is used only in code, never in documents, so it gets no glossary entry (my call).
- **No new token.** The amounts are those of D-59 and D-60, read from `tokens.css`.
- **The fade's stops stay in `window.css`** (`--light-fade`, D-61). `decoration.mjs` holds them as `FADE`, and a spec ties the two, as `GLYPHS` is tied to the gallery (my call; it gives the curve the home D-61 left to P5.3). `FADE` is a list of `[offset, mix]`: `[0.056, 1]`, `[0.127, 0.885]`, `[0.197, 0.772]`, `[0.268, 0.607]`, `[0.338, 0.501]`, `[0.408, 0.386]`, `[0.479, 0.279]`, `[0.549, 0.2]`, `[0.62, 0.122]`, `[0.69, 0.071]`, `[0.831, 0.029]`, `[1, 0]`. Before the first stop, mix is 1; between stops it is linear.
- **The light at a distance.** For a light of colour `c` (alpha `c.a`), length `s` and inset `i` on a side, the alpha `d` logical px out from the window outline's outer edge is `c.a × mix((i + d) / s)`. It is 0 where `(i + d) / s ≥ 1`. The window glow: `glow`, `glow-size`, inset 0 on every side. The shadow: `shadow`, `shadow-size`, and `shadow-inset-top`, `-side` and `-bottom`. With today's tokens, the glow shows for 48 px on every side, and the shadow for 9 px above, 19 px beside and 32 px below.
- **Padding.** `PaddingTop`, `-Left`, `-Right` and `-Bottom` are each the larger of the two lights' reach on that side: `max(glow-size, shadow-size − shadow-inset-<side>)`, 48 on every side today. A reach that is not whole px is refused. The padding belongs to the `rc` file and is shared by both states, so the inactive frame's padding beyond its shadow is transparent.
- **The frame's elements** (`decoration.svg`). The centre stays as D-125 left it. Each edge and corner element holds, from the outside in: `padding` px of light, then `outline-width` px of `outline`. A gradient is written with `stop-color` (`#rrggbb`) and `stop-opacity`, never a colour with alpha. Its stops are those of `FADE` that fall in the element, mapped to the element's thickness, plus one stop at each end with its value interpolated. So no gradient depends on a start that lies outside its element. Edges take a `linearGradient` across their thickness, and corners a `radialGradient`. Where each corner gradient is centred, and whether elements reach inside the window, is Task 1's answer:
  - **Design A**: the inactive frame's elements reach `shadow-inset-<side>` px inside the window outline, filled `tone-0` there. Each corner gradient is centred at the inner point `(shadow-inset-side, shadow-inset-top)`, or the bottom equivalent, as `window.css` centres it. The active frame does not reach in. This draws the prototype exactly. It is chosen if Task 1 finds that Aurorae paints such elements without moving the title bar, the buttons or the application.
  - **Design B**: no element reaches in. Edges run the window's whole length, and each corner is centred on the window outline's outer corner. For the window glow, A and B are the same. For the shadow, B differs from the prototype for the first `shadow-inset-*` px along each side, so it is not chosen without the owner (see "Stop and ask").
- **`Shadow` in `[General]`.** It stays `true` unless Task 1 finds that `true` draws something on the title, such as a text shadow. Then it is `false` (my call: no widget glows or casts a shadow, D-4).
- **Maximised and tiled.** A maximised window shows no window outline, no glow and no shadow. Its title bar is `tone-0`, `title-bar-height` high, from the output's top edge. It shows restore (platform, P5.2), and its close reaches the output's top-right corner. A tiled window keeps the window outline on every edge that does not touch the output's edge, and its light on those sides. Whether KWin drops an edge that touches the output's edge is recorded, not fixed. `decoration-maximized-*` elements are added only if Task 1 finds that a maximised window needs them.
- **What "matches the prototype" means here** (my call):
  1. `image light` passes on each side of an active window over a `tone-0` backdrop, and of an inactive window over a `text` backdrop, within 0.02 alpha, in KWin's shot and in the gallery's alike;
  2. at each corner, a profile along the diagonal out from the window outline's corner passes `image light` against the corner's expected fade, within 0.02;
  3. the window outline stays as D-126 left it: `outline`, `outline-width` px at scale 1, 1 or 2 device px at 1.49;
  4. a maximised window: `tone-0` from the output's top row for `title-bar-height` px, then the application; no `outline` pixel and no light on any edge;
  5. `image lines --blends` and `image greys --token-blends` report nothing over the light and the edges, leaving out the window outline's own rows and columns.
- **Never change the owner's system settings.** At the start and end of Task 1 and of Task 4, `sha256sum ~/.config/kwinrc ~/.config/kdeglobals` gives the same result, and `~/.local/share/aurorae/themes/` is still empty. KWin runs only in the nested session. A probe theme is a folder in `tmp/check-colour-scheme/probe-p5.3/`, linked as `tmp/check-colour-scheme/data/aurorae/themes/amberprobe` and selected in the nested `kwinrc` alone.
- Paths stay inside the repository. `generate decoration --write` writes only the files of `parts/decoration/amber/`. Shots, probes and anything downloaded stay in `tmp/` and are not committed. A file read from the web goes into a new empty folder of its own and is read as text, never run.
- Anti-goals: no rounded corner, no line but the window outline, no cool grey, and no glow but the window glow (D-4). A radial gradient at a corner of the light is not a rounded corner: the window's corners stay square (P0.6).
- **Stop and ask the owner** if any of these happens:
  - Task 1 finds Design A impossible. The owner chooses between Design B, with the prototype changed to draw what B draws, and Design B as a known gap. Show them shots of both corners.
  - Aurorae does not draw the eased fade within 0.02 of the tokens, at scale 1;
  - a click in the light is taken by the window that casts it (Review Focus 1);
  - a maximised window shows any line, or its close does not reach the output's corner;
  - the window outline at 1.49 gets worse than D-126 left it.

**Interfaces:**
- Consumes: `reader` (inside `decoration.mjs`), `loadTokens`, `resolveToken` (`tokens.mjs`), `readPng` (`png.mjs`), `main`, `UsageError` (`cli.mjs`).
- Produces:
  - `FADE` (`decoration.mjs`): the stops of the Global Constraints.
  - `lights(tokens) -> { active: Light, inactive: Light }`, where `Light = { colour: {r, g, b, a}, size: number, inset: { top, left, right, bottom } }`. The glow's insets are 0, and the shadow's left and right insets are `shadow-inset-side`.
  - `fade(light, side: 'top' | 'left' | 'right' | 'bottom', d: number) -> number`: the alpha of the Global Constraints.
  - `cornerFade(light, corner: 'topleft' | 'topright' | 'bottomleft' | 'bottomright', d: number) -> number`: the alpha `d` logical px out along the corner's diagonal from the window outline's outer corner. The gradient is centred as the chosen design centres it.
  - `padding(tokens) -> { top, left, right, bottom }`: whole px, or an `Error` naming the token.
  - `lightAlphas(image, from, to, over: {r, g, b}, light: {r, g, b}) -> number[]` (`image.mjs`): for each pixel from `from` to `to`, a row, column or 45° diagonal, the alpha `a` that best gives `over + a × (light − over)` over the three channels, clamped to 0 to 1.
  - `image light <png> --from x,y --to x,y --over <hex|token> --state active|inactive (--side top|left|right|bottom | --corner <corner>) [--scale 1] [--tolerance 0.02] [--json]`. `from` is the first device pixel outside the window outline, and `to` lies outward. It prints one line per pixel, `3  0.112  0.118  -0.006`, then `max 0.006 (tolerance 0.02)`. Exit 0 within tolerance, 1 beyond, 2 for a usage error. The expected value at device pixel `n` is `fade` at `(n + 0.5) / scale`, or `cornerFade` at `√2 × (n + 0.5) / scale` along a diagonal.
