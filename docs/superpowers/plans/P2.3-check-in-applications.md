# P2.3 Check in applications Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** See `Amber.colors` in Dolphin, Kate and Konsole without changing a system setting, prove by pixels that the colour scheme brings no cool grey, answer the six unverified questions of the platform document's colour-scheme section, and write the findings down.

**Architecture:** A new tool, `image`, reads a PNG (decoded in plain Node with `node:zlib`, no new dependency) and lists the colours of its pixels that are neutral but not warm, by the same rule the prototype check uses (`warmthOffence` and `isHue` of `tools/src/lib/prototype-check.mjs`). The applications run inside a nested KWin, as in P0.4, with their own `XDG_CONFIG_HOME` holding a `kdeglobals` made from `Amber.colors`, and `Amber.colors` found through `XDG_DATA_DIRS`. Pictures are taken inside the nested KWin with Spectacle and read with the tool. A small PySide6 probe window shows the palette roles and widgets the questions need. The nested session's files live in `tmp/` and are not kept; the findings go into `platform.md`, `colour-scheme.md` and, for gaps, the README.

**Tech Stack:** Node 24 ES modules, `node:test`, `node:zlib`, culori 4.0.2 (through `prototype-check.mjs`), the existing `cli.mjs` and `tokens.mjs`; `kwin_wayland` 6.8.2 nested, `spectacle`, `dbus-run-session`, Python 3 with PySide6 6.11.2, Dolphin, Kate 26.08.2, Konsole.

**Spec:** `docs/product/roadmap.md` (row P2.3 and the note under Step 2), `docs/architecture/platform.md` ("Colour scheme" and its "Unverified" table; the nested KWin of "Window decoration"), `docs/architecture/colour-scheme.md` ("Rules", "Roles that are derived", "Generating"), `docs/architecture/design-language.md` (principle 1, "A hue is not a grey"), `docs/architecture/tooling.md` ("Rules for every tool"), `docs/architecture/decisions.md` (D-13, D-86 to D-92).

## Global Constraints

- Branch `feat/p2.3-check-in-applications` from `master`; this plan file is committed on it.
- Use the glossary's words, British spelling: colour scheme, colour set, role, token, known gap, status colour. A cool grey is a neutral that does not lean warm.
- **Never change the owner's system settings.** Nothing under `~/.config` is created or edited, and nothing is written under `~/.local/share`: `Amber.colors` is found through `XDG_DATA_DIRS`, not installed. `sha256sum ~/.config/kdeglobals ~/.config/kwinrc ~/.config/dolphinrc ~/.config/katerc ~/.config/konsolerc` is the same at the start (Task 2) and the end (Task 5). No `plasma-apply-colorscheme`, no `kwriteconfig6` without `--file` into `tmp/`, no `qdbus` on the owner's bus. Every application of this plan runs inside the nested KWin.
- Write nothing under `/usr`.
- The nested session's files live in `tmp/check-colour-scheme/` (ignored by git) and are not committed. Pictures kept as evidence stay there too; the documents describe what they show.
- **Cool grey, as a rule a tool can apply** (my call, the prototype check's rule applied to pixels): a pixel offends when its colour is not a hue (OKLCH chroma below 0.05) and `warmthOffence` is not null (not black, and either no hue at chroma below 0.005 or a hue outside 30 to 110).
- **Every cool grey found is traced to its source** before it is judged: a role of the colour scheme or a colour KColorScheme derives from one (fixed in this plan, in `roles.json` or the rules, then regenerated), the Breeze style's own colours (recorded for the plan of Step 3 that restyles that widget), an icon or the application's own drawing (a known gap candidate), or the decoration of the nested KWin (not part of this check: P5 owns it).
- A fact goes into `platform.md` as verified, with the date of the run, only if it was seen on this machine in this plan.
- **Stop and ask the owner** when a cool grey cannot be removed by the colour scheme and is not owned by a later plan, and before marking the row done if any cool grey from outside the colour scheme remains: whether "No cool grey is visible" holds then is the owner's call.
- No rounded corner, hairline or cool grey: this plan draws nothing of Amber's own. The tool's marked copy (Task 1) is a picture for checking, not a part.

## Review Focus

- **A picture with an alpha channel or of another PNG type.** Spectacle may save RGBA, RGB or a palette PNG. Expected: RGB and RGBA at 8 bits are read; every other type, interlacing and a bad CRC are refused with a message naming the file, never misread (tooling rule 7). Pinned in Task 1.
- **Anti-aliased text.** Text pixels are mixes of text and tone; mixes of two warm colours must not be reported. Pinned in Task 1 by a fixture of mixes, and in Task 3 by reading what is reported in a real picture.
- **The decoration of the nested KWin is in the picture.** It is Breeze's decoration, drawn from `[WM]` or `Header`; its greys would be blamed on the colour scheme. Pinned in Task 3: pictures are cut to the window's content with `--region`, and the decoration is read separately for the `[WM]` question.
- **The applications do not read the isolated `kdeglobals`** and show the owner's Breeze Dark instead, so every pass means nothing. Pinned in Task 2, Step 4: Selection in Dolphin must measure as `accent`, a colour Breeze Dark does not have.
- **A stale `kdeglobals` cache** (`~/.cache/` is the owner's): the nested session gets its own `XDG_CACHE_HOME`. Pinned in Task 2.

### Task 1: The `image` tool

**Files:**
- Create: `tools/src/lib/png.mjs`, `tools/src/lib/png.spec.mjs`
- Create: `tools/src/lib/image.mjs`, `tools/src/lib/image.spec.mjs`
- Create: `tools/src/bin/image.mjs`, `tools/src/bin/image.spec.mjs`
- Modify: `.claude/skills/ai-tools/references/tools.md`, `.claude/skills/ai-tools/SKILL.md` (description names the new tool), `docs/architecture/tooling.md` (row in "Planned tools")

**Interfaces:**
- Consumes: `warmthOffence(text)`, `isHue(text)` from `prototype-check.mjs`; `loadTokens()`, `resolveToken(tokens, name)` from `tokens.mjs`; `main`, `print`, `table` from `cli.mjs`.
- Produces:
  - `decodePng(buffer) -> { width, height, pixels: Uint8Array }` — RGBA, 4 bytes a pixel; throws `Error` naming what is not supported.
  - `encodePng({ width, height, pixels }) -> Buffer` — RGBA, 8 bits, filter 0.
  - `coolGreys(image, { region }) -> Array<{ hex, count, box: { x, y, width, height }, why }>` — offending colours, most pixels first; `region` is `{ x, y, width, height }` or absent for the whole picture. Fully transparent pixels are skipped.
  - `colourCounts(image, { region, tokens }) -> Array<{ hex, count, token? }>` — every colour, most pixels first; `token` is the name of a colour token with exactly that hex, when there is one.
  - `markPixels(image, hexes) -> image` — a copy with every pixel of those colours painted magenta `#ff00ff`.
  - CLI: `image greys <png> [--region x,y,w,h] [--mark <out.png>] [--json]` exits 1 when a cool grey is found; `image colours <png> [--region x,y,w,h] [--top 20] [--json]`. `--mark` writes only to a path inside the repository (rule 6) and is the tool's `--write` (rule 5: the text output says what it wrote).

- [x] **Step 1: Write the failing specs for `png.mjs`.** Round trip: `decodePng(encodePng(img))` equals `img` for a 3 × 2 picture. An RGB picture (colour type 2) built in the spec with `zlib.deflateSync` and filters 1 to 4 on its rows decodes to the right RGBA. Refusals, each with a message containing the reason: not a PNG signature (`not a PNG`), bit depth 16 (`bit depth 16`), colour type 3 (`palette`), interlace 1 (`interlaced`), a broken CRC (`CRC`).

- [x] **Step 2: Run them and see them fail.** `npm --prefix tools test` — FAIL, `png.mjs` not found.

- [x] **Step 3: Implement `png.mjs`.** IHDR, IDAT (joined, then `inflateSync`), IEND; the five filter types with the Paeth predictor; CRC with `zlib.crc32`. Only 8-bit colour types 2 and 6.

- [x] **Step 4: Run and pass.**

- [x] **Step 5: Write the failing specs for `image.mjs`.**
  - A picture of tone 0, tone 2, `text`, `accent` and 20 mixes of `text` over `tone-2` (as anti-aliasing makes) gives `coolGreys` `[]`.
  - Adding 3 pixels of `#808080` and 2 of `#2b2d31` (Breeze Dark's view) gives two entries, `#808080` first with `count: 3`, each with its `box` and a `why` starting `not warm`.
  - `#000000` and a blue `#487a97` (a hue, `--ansi-blue`) are not reported.
  - `region` excludes a grey pixel outside it; a fully transparent `#80808000` pixel is not reported.
  - `colourCounts` names `#151413` as `tone-0` (read from the tokens, not written in the spec) and leaves a non-token colour without `token`.
  - `markPixels` paints only the listed colours.

- [x] **Step 6: Run and see them fail; implement `image.mjs`; run and pass.**

- [x] **Step 7: Write the failing CLI specs** in `tools/src/bin/image.spec.mjs`, with fixtures written by `encodePng` into a temporary folder inside `tmp/`: `greys` on a warm picture exits 0 and prints `no cool grey`; on the grey picture exits 1 and lists `#808080  3 px  at 4,0 1×1` (form of the line my call); `--region 0,0,0,1` is exit 2; `--mark /tmp/x.png` (outside the repository) is exit 2; `--mark tmp/…/out.png` writes the file and prints its path; `colours --top 2 --json` prints two objects.

- [x] **Step 8: Run and see them fail; implement `tools/src/bin/image.mjs`; run and pass.** The whole suite passes: `npm --prefix tools test`.

- [x] **Step 9: Document** the tool in `references/tools.md` (table row, commands, an example each, the rule for a cool grey with its source in `prototype-check.mjs`, what PNGs are read), the skill's description, and the "Planned tools" table of `tooling.md` (`image` | `greys <png> [--region] [--mark]`, `colours <png> [--region] [--top]` | P2.3).
