# P1.3 Gallery: buttons and inputs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A second prototype page, `prototype/gallery.html`, opened from disk. It shows buttons, primary buttons, tool buttons, combo boxes, text fields, spin boxes and text areas in every state side by side, and each control reacts to the pointer and the keyboard. Beside them are candidates for the focused tone (O-3) and for the tone of an empty well (O-1), each with its measured contrast.

**Architecture:** The new tones of widget states become tokens with contrast pairs. The focused tones are opaque colours. Each one is written with the accent mix it came from, so the colour scheme and the Union style can use it as it is. The page is plain HTML and CSS with no script. `widgets.css` draws the widgets, and their states come from the real pseudo-classes (`:hover`, `:focus-visible`, `:active`, `:disabled`) together with forced classes (`.is-hovered`, `.is-focused`, `.is-pressed`, `.is-checked`). That lets one row show every state at once while each copy still reacts. `gallery.css` lays the page out. The page specs read every page instead of `index.html` alone. A spec run in Chrome checks two things: that each state is drawn in the tone the design language gives it, and that a live control in a real state looks the same as its forced copy.

**Tech Stack:** HTML and CSS opened as `file://` (D-35); Node 24 ES modules, `node:test`, `node:assert/strict`; the existing `tokens.mjs`, `prototype-check.mjs` and `browser.mjs` (playwright-core with the installed Chrome, D-46). No new dependency.

**Spec:** `docs/product/roadmap.md` (P1.3 and the paragraph under the Step 1 table), `docs/architecture/design-language.md` (Principles, Widgets, Shadow), `docs/architecture/accessibility.md` (rules 1, 2, 4; "Where Amber departs from WCAG on purpose"), `docs/architecture/decisions.md` (D-4, D-35, D-36, O-1, O-3), `docs/product/glossary.md` (Widget states).

## Global Constraints

- Branch `feat/p1.3-gallery-buttons-and-inputs`; this file is committed on it.
- Use the glossary's words and British spelling. The new term "well edge" goes into the glossary first (Task 1, Step 1).
- No rounded corner, no hairline, no cool grey. No `border`, `outline`, `box-shadow` or `text-decoration` other than `none` or `0`, on any widget, in any state. Every native control is reset with `appearance: none`, `border: 0`, `border-radius: 0`, `outline: none` and `font: inherit`. SVG glyphs use `stroke-linecap: square` and contain no `<line>`.
- Every colour comes from `prototype/tokens.css`. The only exceptions are the colour values in a candidate's `style` attribute. The page has no `<script>`, no `<style>` and no `<hr>`, and a `style` attribute only sets custom properties.
- No `<select>`: Chrome draws its popup itself, with rounded corners and grey. The combo box is a `<button>`, and its popup comes with P1.5.
- Font: `10pt "Noto Sans", sans-serif` (D-7), inherited by every control.
- New tokens and starting values (my call; the owner decides O-1 and O-3 in P1.7):

- Two findings for the documents, measured on 2026-11-11:

## Review Focus

- Chrome's own defaults leak in: a focus ring on `:focus-visible`, the grey placeholder, the spin buttons of a number field, the resize grip of a text area, the autofill fill, and the borders and radius of `<button>` and `<input>`. The Chrome spec checks the rendered anti-goals after each state and reads the computed colour of `::placeholder`. Pinned in Tasks 3 and 4.
- States that combine: focused and hovered, or a disabled control that is hovered. The precedence in Global Constraints holds, and a disabled control does not change. Pinned in Tasks 3 and 4.
- The keyboard: Tab reaches every live control except a disabled one or a spin box's step buttons, and the focused tone shows on the control that has focus. For the spin box, that is the well around the field. Pinned in Task 4.
- A tone changed later that makes a printed candidate ratio stale, or a candidate on the new page that escapes the spec because the spec reads only `index.html`. The page specs read every `prototype/*.html`. Pinned in Tasks 2 and 5.
- A forced copy and a live control drifting apart, for example a rule added for `:hover` but not for `.is-hovered`. The Chrome spec compares them. Pinned in Task 3.
