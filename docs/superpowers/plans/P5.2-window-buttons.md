# P5.2 Window Buttons Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Generate the window decoration's minimise, maximise, restore and close buttons as Aurorae button files from the tokens. Show them in the nested KWin in every state, for active and inactive windows, and match them to the prototype.

**Architecture:** The prototype gets every state of the window buttons as a gallery family, so that "matches the prototype" has something to match: the title bar draws at rest and hovered today, but not pressed, not an inactive window's hover, and not the restore glyph. `tools/src/lib/decoration.mjs` learns the four button files. Each is a KSvg frame with one `<prefix>-center` element per state, a square `title-bar-height` across holding the state's fill and the glyph, drawn as the prototype draws it. `PARTS.decoration` then generates six files. In the nested KWin, `browser states` on the gallery and `image states` on KWin's shots compare each state, as P3.3 did for buttons. This plan does not draw the window glow or shadow, and does not look at maximised or tiled windows beyond the restore button (P5.3).

**Tech Stack:** Node 24 ES modules with `node:test`; the `tokens`, `generate`, `browser` and `image` tools; KWin and Aurorae 6.8.2 (`kwin-6.8.2-3.fc45`, `aurorae-6.8.2-1.fc45`) in the nested `kwin_wayland` session (`tmp/check-colour-scheme/`, with `run.sh`, `in.sh`, `in-x11.sh` and `shot`), whose `XDG_CONFIG_HOME` is `tmp/check-colour-scheme/config`. No new dependency.

**Spec:** `docs/product/roadmap.md` (row P5.2, and the note under Step 5 that P5.1 left for it), `docs/architecture/design-language.md` ("Window decoration": "Window buttons are flat and never glow"), `prototype/window.css` (`.window-button`), `prototype/index.html` (the glyphs), `prototype/gallery.html`, `docs/architecture/platform.md` ("Window decoration", "Amber's frame — P5.1", and the Xwayland notes of P3.8), `docs/architecture/decisions.md` (D-4, D-25, D-34, D-100, D-108, D-125, D-126), `docs/architecture/accessibility.md`, `docs/architecture/tooling.md`.

## Global Constraints

- Branch `feat/p5.2-window-buttons` from `master`; this plan file is committed on it in Task 1.
- Glossary words: **window decoration** ("decoration"), **title bar**, **window outline**, **at rest**, **hovered**, **pressed**, **disabled**, **active** and **inactive** for windows, **tone**, **token**, **part**. "Window button" names minimise, maximise, restore and close; it is already in the design language. Add it to the glossary, under "The parts" after **Window decoration**, before using it in code (Task 1): "**Window button**: one of the buttons a window decoration draws in the title bar: minimise, maximise (restore when the window is maximised) and close. _Avoid_ "title bar button" and "caption button"."
- **The state table** (my call, from `window.css`; the pressed rows are new). Fill / glyph:

  | State | Aurorae prefix | Minimise, maximise, restore | Close |
  |---|---|---|---|
  | At rest, active window | `active` | `tone-0` / `text` | `tone-0` / `text` |
  | Hovered, active | `hover` | `tone-1` / `text` | `danger` / `on-danger` |
  | Pressed, active | `pressed` | `tone-2` / `text` | `danger` / `on-danger` |
  | At rest, inactive window | `inactive` | `tone-0` / `text-dim` | `tone-0` / `text-dim` |
  | Hovered, inactive | `hover-inactive` | `tone-1` / `text-dim` | `danger` / `on-danger` |
  | Pressed, inactive | `pressed-inactive` | `tone-2` / `text-dim` | `danger` / `on-danger` |

  Pressed goes one tone past hovered, as a pressed thumb is the lightest thumb. A pressed close stays danger, as a tab's close button does (D-108). Every pair here is already declared in `contrast-pairs.json` (`text` and `text-dim` on tones 0 to 2, `on-danger` on `danger`). No `deactivated` element is drawn: see Task 3 Step 5.
- **Glyphs** are those of `index.html`, in a 16-unit box centred in the button: minimise `M3 8.5h10`, maximise `M3.5 3.5h9v9h-9z`, close `M4 4l8 8M12 4l-8 8`. Restore is new (my call): two squares, the front one whole and the back one showing its top and right edges only, `M3.5 6h6.5v6.5h-6.5zM6 6V3.5h6.5V10H10`. Stroke `currentColor` 1.5 wide, square caps, no fill.
- **Size**: a window button is a square `title-bar-height` across (30 px). `window.css` uses `var(--title-bar-height)` for it, in place of its own `30px`. No new token: the glyph's 16-unit box and 1.5 stroke are drawing, kept in `window.css` and `decoration.mjs`, and a spec ties the two.
- **The button files** (`close.svg`, `minimize.svg`, `maximize.svg`, `restore.svg`; Aurorae's names, unverified until Task 3 Step 2). Each holds, for each prefix of the table in that order, `<g id="<prefix>-center">` with a `<rect>` `title-bar-height` square in the fill (opaque `#rrggbb`), then the glyph's `<path>` translated by `(title-bar-height − 16) / 2` in the glyph colour. The groups sit side by side, 8 px apart, as the frames of `decoration.svg` do. The file starts with the same XML comments as `decoration.svg`, with no double hyphen in them (P5.1). That KSvg takes a lone `-center` element as the whole button, without stretching the glyph, is unverified until Task 3 Step 2.
- **`amberrc`** gains `ButtonMarginTop=0` in `[Layout]` (my call: the button fills the title bar from the window outline down). The other keys stay as D-125 set them; `ButtonWidth` and `ButtonHeight` are already `title-bar-height`, and `ButtonSpacing` 0.
- **Which buttons show is KWin's setting** (`ButtonsOnLeft`, `ButtonsOnRight`), not the theme's. KWin's defaults (unverified, read in Task 3 Step 1) put the menu and on-all-desktops buttons on the left and help, minimise, maximise and close on the right. A button with no file is not shown, except the menu button, which shows the application's icon (P0.4). The nested `kwinrc` is set back to KWin's defaults for this plan, by removing `ButtonsOnLeft` and `ButtonsOnRight`, so that what the owner will see after installing is what is checked.
- **What "matches the prototype" means here** (my call):
  1. each state's fill and glyph colour, read by `image states` from KWin's shot, is the one `browser states` reads from the gallery, ignoring anti-aliased blends between the glyph and its fill;
  2. the buttons sit at the right of the title bar, minimise, maximise, close, with no gap between them and none between close and the window outline; a hovered close's danger runs to the window outline, which stays `outline` on the top and right (`image profile`);
  3. the glyph is centred on its button within 1 device px;
  4. the title stays centred as P5.1 left it, within 2 px of the prototype's, or the owner decides (Task 3 Step 4).
- **Never change the owner's system settings.** At the start and end of Task 3, `sha256sum ~/.config/kwinrc ~/.config/kdeglobals` gives the same result, and `~/.local/share/aurorae/themes/` is still empty. KWin runs only in the nested session, through P5.1's link.
- Pointer states in KWin: tried in this order, the first that reaches hovered and pressed wins, and each is written in the findings: XTest under Xwayland (`KWIN_EXTRA=--xwayland run.sh`, `xdotool mousemove` and `mousedown` over a button; it asks the Remote Control portal first, as P3.8 found); then the owner's own pointer, with `sleep 5; shot <name>` started first. A pressed button is shot while the button is held; the owner then drags off the button before letting go, so that nothing is minimised or closed.
- Paths stay inside the repository. `generate decoration --write` writes only the six files of `parts/decoration/amber/`. Shots and probes stay in `tmp/` and are not committed.
- Anti-goals: no rounded corner, no line but the window outline, no cool grey, no glow (D-4). Task 3 runs `image lines` and `image greys --token-blends` over each shot of a button, leaving out the window outline.
- **Stop and ask the owner** if any of these happens:
  - Aurorae stretches or shifts the glyph, or shows no button, with the files as the Global Constraints give them;
  - a disabled window button shows (Task 3 Step 5): which tones it takes is the owner's;
  - the restore button of a maximised window shows its pressed state at rest (Review Focus 1);
  - the menu button or the title's position differs from the prototype (Task 3 Step 4);
  - a hovered close covers the window outline at any scale.

## Review Focus

1. **The restore button of a maximised window.** Aurorae's QML shows the pressed element when a button is `toggled`, and a maximised window's maximise button may be toggled. Expected: the restore button at rest looks at rest. Pinned in Task 3 Step 5 by a shot of a maximised window with the pointer away from it, read by `image states` against the gallery's restore at rest.
2. **KWin's default buttons.** On a fresh system the menu button, the application's icon, sits at the left of the title bar, where the prototype has nothing, and the button group on the right may push the centred title to the left. Expected: the owner sees it and decides (README advice, or a known gap). Pinned in Task 3 Step 4 by a profile along the title bar's middle row, compared with the prototype's.
3. **The fractional scale.** At 1.49 a 30 px button is 44.7 device px, and P5.1 found the window outline 1 or 2 device px wide (D-126). Expected: no seam of another colour between buttons, or between a hovered button and the title bar or the window outline, and the glyph blended evenly. Pinned in Task 3 Step 6 by profiles at 1.49 across the hovered close's top and right edges and along the row through all three buttons.
4. **A title longer than the space left by the buttons.** Expected: KWin elides it before the first button; no character is drawn under a button. Pinned in Task 3 Step 4 by P5.1's 300-character window, profiled along the title's row up to minimise.
5. **A stale generated file**: a token changes and a button file is not regenerated. Expected: the tests fail and name the command. Pinned by `the decoration is up to date`, which now compares all six files (Task 2).

### Task 2: The button files and `generate decoration`

**Files:**
- Modify: `tools/src/lib/decoration.mjs`, `tools/src/lib/decoration.spec.mjs`, `tools/src/lib/amber-decoration.spec.mjs`, `tools/src/bin/generate.spec.mjs`

**Interfaces:**
- Consumes: `reader`, `hexOf`, `SPDX`, `GENERATED`, `DO_NOT_EDIT_SVG` (inside `decoration.mjs`); `PARTS`, `writePart` (`generate.mjs`).
- Produces:
  - `BUTTON_STATES`: the six prefixes, in the table's order, each `{ prefix, fill: { plain, close }, glyph: { plain, close } }` naming tokens.
  - `GLYPHS`: `{ minimize, maximize, restore, close }`, the path data of the Global Constraints.
  - `formatButtonSvg(tokens, button: 'minimize' | 'maximize' | 'restore' | 'close') -> string`: the whole file. It collects problems as `reader` does, and throws one `Error` naming each.
  - `PARTS.decoration.generate(tokens)` returns `decoration.svg`, `amberrc` and the four `<button>.svg`.

- [ ] **Step 1: Write the failing specs.**
  - `decoration.spec.mjs`, with P5.1's small tokens plus `tone-1 #1c1a18`, `tone-2 #25221f`, `danger #b5442f` and `on-danger #fbf3e6`:
    - `draws every state of a button`: for each button, the ids are exactly `<prefix>-center` for the six prefixes, in order.
    - `fills each state`: in `minimize.svg`, `hover-center`'s rect has `fill="#1c1a18"` and `pressed-center`'s `#25221f`. In `close.svg`, `hover-center`, `pressed-center`, `hover-inactive-center` and `pressed-inactive-center` have `#b5442f`, with the path stroked `#fbf3e6`.
    - `dims the inactive glyph`: `inactive-center`'s path in `maximize.svg` is stroked `#a9a297`; `active-center`'s `#e6dfd3`.
    - `sizes the button by the title bar`: with `title-bar-height 36px`, each rect is 36 × 36 and the path is translated by 10.
    - `draws the glyph as the prototype`: each path's `d` is that of `GLYPHS`, with `stroke-width="1.5"`, `stroke-linecap="square"` and `fill="none"`.
    - `keeps the buttons at the top`: `amberrc` has `ButtonMarginTop=0`.
    - `refuses a fill that is not opaque`: `danger` at 50 % gives an error matching `/danger: .*not opaque/`.
    - `holds no double hyphen in a comment`, and `is the same each time`, for each button file.
  - `amber-decoration.spec.mjs`:
    - `the decoration is up to date` covers the six files.
    - `matches the prototype's window buttons`: for each state of the table, the tokens `BUTTON_STATES` names are those `window.css` gives the matching gallery state, read from the CSS, not copied. The glyph box (16) and stroke (1.5) equal `window.css`'s `.window-button svg`, and `GLYPHS` equals the gallery's paths.
  - `generate.spec.mjs` (bin): `reports each file as JSON` expects six entries.
