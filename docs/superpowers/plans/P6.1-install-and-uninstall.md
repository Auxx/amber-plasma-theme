# P6.1 Install and Uninstall Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `scripts/install.sh` puts all five parts into the owner's home folder with one command, and `scripts/uninstall.sh` takes them out with one command and leaves no file behind.

**Architecture:** The parts are already generated and committed (D-92), so both scripts are plain Bash and need no Node. Install copies each part from `parts/` to its folder under the data home, as the overview's table of parts lists them. It writes an **install record**: every file it wrote and every folder it created. Uninstall reads the record. It removes those files and Amber's Union cache file, then removes the folders that install created, if they are empty. Last, it removes the record. Union's handling of the data home and its cache file are not verified yet, so Task 1 is a probe in the nested session. A spec in `tools/` runs both scripts in a throwaway home and compares the whole tree before and after. Task 3 installs into the nested session and checks that every application finds its part. Task 4 is the owner's round trip on the real home folder.

**Tech Stack:** Bash 5 (`set -euo pipefail`), coreutils (`cp`, `install`, `rmdir`, `sha256sum`). Node 24 with `node:test` and `node:child_process` for the spec. The nested `kwin_wayland` 6.8.2 session (`tmp/check-colour-scheme/`, with `run.sh`, `in.sh` and `shot`), Dolphin, Konsole, `ksyntaxhighlighter6`, and the `image` tool. No new dependency.

**Spec:** `docs/product/roadmap.md` (row P6.1, and the notes P5.1 to P5.3 left for Step 6). `docs/product/vision.md` ("What success looks like": "Installing and uninstalling each take one command, and uninstalling leaves the system as it was"). `docs/architecture/overview.md` ("The parts", "Repository layout", "Rules that hold everywhere"). `docs/architecture/platform.md` ("Union" and "Tools and switches", spike P0.3's "What it changes", "Amber's frame — P5.1", and "Konsole and Kate"). `docs/architecture/decisions.md` (D-24, D-40, D-92). `docs/superpowers/specs/2026-11-10-amber-theme-design.md` (the list of parts and where each is installed).

## Global Constraints

- **Before you start:** P5.3 is merged into `master`. Then create branch `feat/p6.1-install-and-uninstall` from `master`. This plan file is committed on it in Task 1.
- Glossary words: **part**, **colour scheme**, **Union style** ("style"), **window decoration** ("decoration"), **terminal colours**, **editor theme**, **known gap**. One new term, **install record**, goes into the glossary in Task 2, before any other document uses it.
- **Where each part goes.** `D` is `$XDG_DATA_HOME` if it is set to an absolute path, and `$HOME/.local/share` otherwise. A relative `XDG_DATA_HOME` is ignored, as the XDG specification asks.

  | Part | From | To |
  |---|---|---|
  | Colour scheme | `parts/colour-scheme/Amber.colors` | `D/color-schemes/Amber.colors` |
  | Union style | `parts/union-style/amber/` (whole tree) | `D/union/styles/amber/` |
  | Decoration | `parts/decoration/amber/` (its 7 files) | `D/aurorae/themes/amber/` |
  | Terminal colours | `parts/terminal-colours/Amber.colorscheme` | `D/konsole/Amber.colorscheme` |
  | Editor theme | `parts/editor-theme/Amber.theme` | `D/org.kde.syntax-highlighting/themes/Amber.theme` |

  Only the generated or shipped files are copied. `roles.json`, `keys.json` and `styles.json` are not.
- **The style is copied by the script, not by `union-styletool install`** (my call, D-134). P0.3 verified that `union-styletool install` only copies the folder and writes nothing else. A plain copy honours `XDG_DATA_HOME`, so the spec can run in a throwaway home. If Task 1 finds that Union does not read the copied style, stop and ask.
- **The install record** is `D/amber/installed`, a text file with one line per entry: `file <path>` or `dir <path>`, with absolute paths, in the order they were made (my call, D-135). `dir` lines name only folders that install created. A folder that already existed, such as the owner's `~/.local/share/konsole/`, is never listed and never removed.
- **Union's cache file.** Uninstall also removes Amber's cache file in `C/union/`. `C` is `$XDG_CACHE_HOME` if it is absolute, and `$HOME/.cache` otherwise. How that file is found is Task 1's answer (P0.3: Union does not remove it). It is never found by date. No other cache file is removed. Install never creates `C/union/`; Union does, when an application first uses the style. So when `C/union/` does not exist at install time, the record gets an `absent <path>` line for it, and uninstall removes that folder if it is empty (my call).
- **`AMBER_PARTS`**, if set, names the folder the parts are copied from, in place of the repository's `parts/`. It exists for Task 3's trial of a changed part, and the README does not mention it (my call).
- **The scripts write nothing outside `D`, `C` and the record.** Nothing under `~/.config`, nothing under `/usr`, and no setting is changed (D-24, D-40). Neither script runs `plasma-apply-colorscheme`, `kwriteconfig6`, `union-styletool` or `kpackagetool6`.
- **Uninstall reports a selection, and does not undo it.** It reads `$XDG_CONFIG_HOME` (or `$HOME/.config`): `ColorScheme=Amber` in `kdeglobals`, `theme=__aurorae__svg__amber` in `kwinrc`. For each one it finds, it prints one line that names the setting and tells the owner to choose another in System Settings. Then it still uninstalls and exits 0 (my call, D-136).
- **Install refuses to overwrite a file that Amber did not write.** If a target file exists and no install record lists it, install writes nothing, prints each such path, and exits 1. If the record exists, install first runs uninstall's removal, quietly, and then installs again. So a second install leaves the same tree as one install.
- **Exit codes, as the tools use them:** 0 success; 1 an error or a refusal; 2 a wrong command line. Neither script takes an argument except `--help`. Any other argument gives exit 2.
- Both scripts work from any working folder: they find the repository from their own path. They quote every path, so a home folder with a space in its name works. Output is plain text, one line per part, for example `colour scheme → /home/…/color-schemes/Amber.colors`.
- **Never change the owner's system settings.** At the start and end of Tasks 1, 3 and 4, `sha256sum ~/.config/kwinrc ~/.config/kdeglobals` gives the same result. Tasks 1 and 3 run only in the nested session. The only task that writes to the real home folder is Task 4, and the owner runs it.
- Anti-goals: these scripts draw nothing. They copy files that earlier plans checked. Task 3's shots are still read with `image greys --token-blends` and `image lines --blends`, to catch a part that was not found and fell back to Breeze.
- **Stop and ask the owner** if any of these happens:
  - Union does not find a style that was copied into the data home (Task 1);
  - Amber's cache file cannot be told from the others, other than by date (Task 1);
  - KWin does not find the decoration in the data home (Task 3);
  - the round trip on the real home folder leaves any difference (Task 4).

## Review Focus

1. **Folders that already existed.** On the owner's machine, `~/.local/share/aurorae/themes/` and `~/.local/share/color-schemes/` exist and are empty, and `~/.local/share/konsole/` holds `Profile 1.profile`. Expected: after a round trip, all three exist, with the same contents. `union/` and `org.kde.syntax-highlighting/` did not exist, so they are gone. Pinned in Task 2's spec, case `keeps folders it did not create`.
2. **A file the owner added inside a part's folder**, such as an extra `.css` in `D/union/styles/amber/contents/css/`. Expected: uninstall removes Amber's files, leaves the folder with the owner's file in it, prints that path, and exits 0. Pinned in Task 2's spec, case `leaves a foreign file and says so`.
3. **Install over an earlier install**, as after a token was changed and the parts were generated again. Expected: one install record, the new files, and a tree equal to a single install. Union does not keep drawing the old style from its cache. Pinned in Task 2's spec, case `installs twice like once`, and in Task 3, Step 4, with a changed style.
4. **Uninstall while Amber is selected.** Expected: the files go, a line names each setting that still names Amber, `~/.config` is untouched, and the exit code is 0. Pinned in Task 2's spec, case `reports a selection and changes no setting`.
5. **An unusual environment:** `XDG_DATA_HOME` set to a relative path, a home folder whose name has a space, or a script started from another folder. Expected: the parts land in `$HOME/.local/share`, and nothing is written into the working folder. Pinned in Task 2's spec, cases `ignores a relative XDG_DATA_HOME` and `runs from any folder with spaces in HOME`.

- [ ] **Step 1: Write the failing spec.** Each case makes a temporary folder `root/` with a `home/` inside it. It runs `bash <repo>/scripts/<name>.sh` through `spawnSync`, with `env` holding only `PATH`, `HOME=root/home` and the variables the case names. The working folder is `root/`, except where a case says otherwise. The helper `snapshot(dir)` returns a sorted list of `[relative path, sha256 or "dir"]` for every entry under `dir`. The cases:
  - `installs every part`: with an empty home, exit 0. Each target in the Global Constraints' table exists, and its bytes match the source. `D/amber/installed` has a `file` line for each of those files, a `dir` line for every folder install created (in an empty home, `.local` and `.local/share` too), and `absent <home>/.cache/union`.
  - `round trip on an empty home`: after install and then uninstall, `snapshot(root)` equals the one taken before install.
  - `keeps folders it did not create`: the home holds `.local/share/aurorae/themes/`, an empty `.local/share/color-schemes/`, `.local/share/konsole/Profile 1.profile` and `.cache/union/<foreign>`. After a round trip the snapshot is unchanged.
  - `removes Amber's cache file only`: after install, put a cache file named or filled by Task 1's rule, plus a foreign one, in `.cache/union/`. After uninstall only the foreign file is left.
  - `installs twice like once`: install, install, then compare the snapshot with a single install in a fresh home; then uninstall, and the home matches its first snapshot.
  - `refuses a file it did not write`: `.local/share/color-schemes/Amber.colors` holds `mine`. Install exits 1, its stderr names that path, and the snapshot is unchanged.
  - `leaves a foreign file and says so`: after install, add `extra.css` beside `style.css`. Uninstall exits 0, `extra.css` and its folders remain, the rest of Amber's files are gone, and stdout names `extra.css`.
  - `reports a selection and changes no setting`: `.config/kdeglobals` holds `[General]\nColorScheme=Amber`, and `.config/kwinrc` holds `[org.kde.kdecoration2]\ntheme=__aurorae__svg__amber`. Uninstall exits 0, stdout names both, and `.config/` is byte for byte the same.
  - `uninstall with nothing installed`: exit 0, stdout says nothing is installed, and the snapshot is unchanged.
  - `honours an absolute XDG_DATA_HOME and XDG_CACHE_HOME`: with both set to folders under `root/`, the parts land there and `home/` stays empty, and a round trip restores both.
  - `ignores a relative XDG_DATA_HOME`: with `XDG_DATA_HOME=rel`, the parts land in `home/.local/share` and no `root/rel` appears.
  - `runs from any folder with spaces in HOME`: `HOME=root/my home`, the working folder is `/`, and the round trip succeeds.
  - `writes nothing outside HOME`: across every case, `snapshot(root)` differs from the start only under `home/` or the case's XDG folders.
  - `rejects arguments`: `install.sh --bogus` exits 2, and `--help` exits 0 and prints usage.
- [ ] **Step 2: Run it and see it fail.** `npm --prefix tools test`. Expected: FAIL, because `scripts/install.sh` does not exist.
- [ ] **Step 3: Write `scripts/lib.sh`, `scripts/install.sh` and `scripts/uninstall.sh`** as the Global Constraints say. Install first checks every target for a refusal and writes nothing until all of them pass. It writes the record line by line as it goes, so that an install that fails halfway can still be uninstalled. Uninstall removes in reverse order of the record and uses `rmdir`, never `rm -r`, for folders. Each script starts with the SPDX header of the repository's other hand-written files (MIT).
