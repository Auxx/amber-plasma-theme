# P2.1 Role mapping Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every role of a `.colors` file a token or a written rule, in a table that the generator of P2.2 reads, and fail the tests when a role is missing or when a pairing the colour scheme makes has no contrast pair.

**Architecture:** The table is `parts/colour-scheme/roles.json`. It is written by hand and refers to tokens by name (overview: "content of a part that is not a value… refers to values by name"). A new library, `tools/src/lib/colour-scheme.mjs`, holds the list of roles a `.colors` file has, reads the table and checks it. A spec over the real files checks four things: every role is covered, every token exists, every foreground on its set's backgrounds is a declared contrast pair, and no hover frame shows. Five new text tokens (link, visited and the three status colours) fill the roles Amber had no token for. Each points to a colour the owner has already approved, and the gallery shows them.

**Tech Stack:** Node 24 ES modules, `node:test`, the existing `tools/src/lib/tokens.mjs` and `colour.mjs`, and the existing `browser.mjs` for the gallery. No new dependency, and no new command: the generator of P2.2 is the first command to read the table.

**Spec:** `docs/product/roadmap.md` (P2.1), `docs/architecture/overview.md` (how it fits, the parts), `docs/architecture/accessibility.md` (rules 1–2, how the check works), `docs/architecture/decisions.md` (D-4, D-33, D-72, D-75), and the owner's three answers of 2026-11-12, given before this plan was written (D-86 to D-88 below).

## Global Constraints

- Use the glossary's words, British spelling. The new terms **Colour set**, **Role** and **Status colour** go into the glossary before they are used anywhere else (Task 1, Step 1).
- The role list is verified on this machine (2026-11-12): kf6-kcolorscheme 6.31.0 (`strings` of `libKF6ColorScheme.so.6`), and `/usr/share/color-schemes/BreezeDark.colors` of plasma-workspace 6.8.2. There are seven colour sets, `View`, `Window`, `Button`, `Selection`, `Tooltip`, `Complementary` and `Header`, plus `Header][Inactive`. Each has the same 12 keys: `BackgroundNormal`, `BackgroundAlternate`, `ForegroundNormal`, `ForegroundInactive`, `ForegroundActive`, `ForegroundLink`, `ForegroundVisited`, `ForegroundNegative`, `ForegroundNeutral`, `ForegroundPositive`, `DecorationFocus`, `DecorationHover`.
- Owner's answers of 2026-11-12 (D-86 to D-88):
  - Selection is an accent fill with on-accent text.
  - The link and status colours point to approved colours: `link` → `syntax-function`, `visited` → `syntax-keyword`, `positive` → `syntax-string`, `negative` → `syntax-number`, `neutral` → `accent`.
  - DecorationFocus is accent (on-accent in Selection), and DecorationHover equals its set's BackgroundNormal.
- Measured on 2026-11-12: on tones 0–4, the lowest ratio of each new token is link 5.10:1, visited 5.13:1, positive 5.17:1, negative 5.14:1 and neutral 5.63:1, all on tone 4. Their pairs have a minimum of 4.5 (rule 1).
- Every value in a colour set is a token, never a literal colour. Literal values are allowed only outside the colour sets (effects, `General`, `KDE`), and each needs a `why`.
- No rounded corner, hairline or cool grey. The gallery row draws text only. The table puts no neutral grey in the file: the `Color` of each effect is a warm token, although the effect does not use it.
- Never change the owner's system settings. Reading files under `/usr` is fine; writing there is not.

`←` means the same token as in Window. The reasons, written once in `roles.json` as the `why` of the first entry each applies to:

- **Window tone 2, alternate tone 1:** the main surface and a sidebar (shell).
- **View tone 2 with no alternate:** lists in the prototype are tone 2 with no stripes. A well (tone 0) is drawn by the Union style from its own variable, not from the View set (overview: "tones the scheme cannot express are defined in the style's own variables"). Outside the style, a text field shows tone 2: this is a known gap if P2.3 sees it.
- **Button tone 3, alternate tone 4:** a raised widget and a hovered one.
- **Header tone 0, alternate tone 1:** the title bar and toolbar are tone 0. Header][Inactive is the same, because an inactive window is shown by the decoration (glow or shadow, dim title), not by a toolbar tone.
- **Tooltip popup:** popups are tone 3.
- **Complementary tone 0, alternate tone 1:** the darkest surface. Plasma's shell is out of scope (D-18), but applications use this set for overlays.
- **Selection all on-accent:** status colours lose their hue on a selection, as Breeze's do, and every text keeps 8.72:1.

## Review Focus

- **A token in the table that does not exist** (a typo such as `tone-5`): the spec names the group, the key and the token. It does not fall back to anything.
- **A pairing the scheme makes with no contrast pair**, for example a change of Button's alternate to a tone where dim text is not declared: the spec names set, role, token and background, and fails.
- **A literal colour inside a colour set** (`"value": "#808080"`): refused by the parser, since a set must take tokens and a literal could bring back a grey.
- **A key added by a newer Plasma** (Breeze Dark gains a role): the system-file test names the new key, so that the table cannot fall behind unnoticed. It skips, saying why, when the file is absent.
- **Hover frames showing**: DecorationHover differing from BackgroundNormal in any set fails the spec, since D-4 rules out an outline as a state.

### Task 2: Colour-scheme library

**Files:**
- Create: `tools/src/lib/colour-scheme.mjs`
- Test: `tools/src/lib/colour-scheme.spec.mjs`

**Interfaces:**
- Consumes: `resolveToken(tokens, name)`, `Pair` from `tokens.mjs`; `srgb8` from `colour.mjs`.
- Produces, from `colour-scheme.mjs`:
  - `ROLES_FILE`: absolute path of `parts/colour-scheme/roles.json`, resolved from `import.meta.url`.
  - `COLOUR_SETS: string[]`: the eight set groups, `'Colors:View'` … `'Colors:Header][Inactive'`.
  - `SET_ROLES: string[]`: the 12 keys, in the order of the Global Constraints.
  - `OTHER_ROLES: Record<string, string[]>`: the keys of `ColorEffects:Disabled`, `ColorEffects:Inactive`, `General` (`ColorScheme`, `Name`, `shadeSortColumn`), `KDE` (`contrast`, `frameContrast`) and `WM`, as in the table above. The comment above it cites the versions it was verified on.
  - `parseRoles(source: string, file = 'roles.json'): Map<string, Map<string, Entry>>`. `Entry` is `{ token: string, why?: string } | { value: string | number | boolean, why: string } | { rule: string, why?: string }`. It throws `<file>: <group>.<key>: <reason>` on:
    - a group not in `COLOUR_SETS` or `OTHER_ROLES`, or a key not known for its group;
    - an entry that has none, or more than one, of `token`, `value` and `rule`;
    - a `value` without `why`;
    - a `value` or `rule` inside a colour set.
  - `loadRoles(file = ROLES_FILE)`.
  - `missingRoles(roles): string[]`: each `group.key` that has no entry.
  - `unknownTokens(roles, tokens): string[]`: `group.key: <token>` for each token that `resolveToken` cannot resolve.
  - `uncheckedPairings(roles, tokens, pairs): string[]`: for each colour set, each `Foreground*` token on the set's `BackgroundNormal` and `BackgroundAlternate` needs a declared pair with a minimum of at least 4.5, and `DecorationFocus` needs one of at least 3. A pair counts when it has one background layer and its foreground and background resolve to the same colours (compared as `srgb8` hex), so that `popup` matches pairs declared on `tone-3`. Each miss reads `Colors:Button.ForegroundLink (link) on BackgroundAlternate (tone-4): no pair of 4.5`.
  - `visibleHoverFrames(roles, tokens): string[]`: each colour set whose `DecorationHover` and `BackgroundNormal` resolve to different colours.

- [ ] **Step 1: Write the failing tests** with inline JSON and an inline token map built by `parseTokens` (`--a: #000000; --b: #ffffff; --c: var(--a);`) and inline pairs built by `parsePairs`. Tests:
  - `knows the roles`: `COLOUR_SETS.length` is 8, `SET_ROLES.length` is 12, `OTHER_ROLES.WM.length` is 6.
  - `reads entries of each kind`: a fixture with one `token`, one `value` with `why` and one `rule` parses, and `.get('General').get('Name')` deep-equals `{ value: 'Amber', why: 'its name' }`.
  - `refuses what it does not understand`: each throws and matches:
    - unknown group `Colors:Sidebar` → `/roles.json: Colors:Sidebar/`;
    - unknown key `Colors:View.ForegroundLoud` → `/Colors:View.ForegroundLoud/`;
    - `{ token: 'a', value: 1, why: 'x' }` → `/exactly one/`;
    - `{ value: 0 }` → `/why/`;
    - `{ value: '#808080', why: 'x' }` in `Colors:View` → `/token/`.
  - `lists missing roles`: a fixture with only `Colors:View.BackgroundNormal` reports 122 entries (8 × 12 set roles, plus 7 + 9 + 3 + 2 + 6 other roles, minus the one present), including `'Colors:Header][Inactive.DecorationHover'`.
  - `names unknown tokens`: `{ token: 'nope' }` gives `['Colors:View.BackgroundNormal: nope']`.
  - `finds unchecked pairings`: a View set with ForegroundNormal `b` on `a` and a pair `b on c` at 4.5 has no miss for it (matched through `c` → `a`). With the pair's minimum at 3, it reports the miss.
  - `finds hover frames`: DecorationHover `b` with BackgroundNormal `a` gives `['Colors:View']`; `c` with `a` gives `[]`.
